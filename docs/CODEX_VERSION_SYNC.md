# Codex 版本同步：诊断与恢复

本功能跟随 `openai/codex` 的 `rust-v` 稳定发布，更新网关的规范客户端身份；不修改模型目录、定价、账号权限或客户端入站版本限制。

## 后台展示

在「系统设置 → 网关服务 → 自动同步 Codex 版本号」下，默认只有一行：生效版本、版本来源、最近检查结果。点击原生折叠详情查看检查时间、成功时间、版本更新时间、失败分类和下次检查时间。手动固定版本时另外提示如何恢复自动跟随。

展示的是已保存的配置，不把尚未保存的表单输入冒充生效值。版本来源与出站规范身份复用同一选择函数：手动值 → 已同步值 → 内置版本。关闭自动同步只停止获取新版本，不清空已同步值。

管理员只读接口：`GET /api/v1/admin/settings/openai-codex-version-sync`。读取状态及「刷新状态」都不调用 GitHub。前端仅在网关页和浏览器可见时每分钟读取本地快照，保存设置后立即刷新，并丢弃迟到的旧响应；读取失败显示「状态暂不可用」，不保留旧的成功提示。

## 时间与持久化语义

- `last_checked_at`：最近完成的检查的开始时间。
- `last_succeeded_at`：最近一次完整检查成功的时间，版本没有变化也会刷新。
- `last_version_updated_at`：同步版本设置行的真实更新时间，仅版本向前推进时变化；老实例不能用这个值推断最近成功检查。
- `next_check_at`：当前安排的下一次检查或恢复重试，不是承诺届时一定成功。
- `rate_limit_reset_at`：GitHub 提供的主额度窗口重置时间，不是 ChatGPT/Codex 使用额度。

一条任务独占写入的 JSON 设置 `openai_codex_version_sync_state` 保存检查结果、下一次检查时间和追加重试次数，不需要数据库迁移，不进入通用设置写入。进程重启后恢复未过期的冷却和预算；已有成功检查但版本未变化时，也不会因旧版本行时间而重复启动检查。旧实例无状态记录时保留原有版本行防抖，成功检查历史仍显示未知。

每次 GitHub 检查整体最多 30 秒；结果保存使用独立的 5 秒超时，避免请求超时后连失败记录都无法写入。保存状态失败会记录受控服务端事件，并保留本实例的内存快照供后台提示「检查结果未保存」，不会以数据库旧成功记录掩盖新失败；该内存快照无法跨重启或跨副本恢复，不清空版本。任务停止会取消在途请求和定时器。同一进程的检查串行执行，重复 Start 不启动第二个任务。

## 失败恢复规则

正常检查间隔保持六小时。从最近一次完成的检查起计算下一次常规检查，不因重试而在窗口重置前被旧 ticker 再次唤醒。

| 失败 | 行为 |
| --- | --- |
| 403/429，`X-RateLimit-Remaining=0` | 识别主限流，等待 `X-RateLimit-Reset`；若还有 `Retry-After`，取更晚期限 |
| 次级限流消息、`Retry-After` 或其他 429 | 遵守等待期限，至少一分钟并指数退避 |
| 网络失败、超时、GitHub 5xx | 有界的一、二、四分钟恢复退避 |
| 普通 401/403、无稳定发布、设置读写失败 | 记录明确分类，等待常规周期，不把权限错误误判为额度问题 |

每个常规周期最多追加三次恢复检查，附加五秒安全余量及零至九秒抖动。预算耗尽后回到常规周期，仍不得早于已知上游冷却期限。主端点限流或鉴权失败后不请求共享同一 REST 额度的发布列表；其他组件成为 latest 或主端点临时故障时仍保留原有列表回退。

解析 `Date` 以计算服务器期限对应的本机相对等待，避免时钟偏快提前请求。只读取最多 8 KiB 错误消息来分类，不把原始消息、URL、请求头、令牌或代理凭据写入状态、日志或管理响应。错误分类不依赖完整响应体，空体主限流也能从响应头识别。

额度重置不是成功保证：同出口的其他进程仍可能消耗额度，多副本也仍各自运行同步任务。本补丁没有引入分布式领导者或跨副本互斥；重启防抖、持久化冷却、有界预算及抖动减少请求放大，但不宣称实现集群级严格单次检查。

## 部署与回退

GitHub 认证已由现有 `UPDATE_GITHUB_TOKEN` 支持，无需为本功能增加令牌输入框。该环境变量在发布客户端构造时读取，调整部署配置后需重建或重启进程加载。不要将令牌提交到仓库或 PR。

升级后先观察最近成功检查与同步版本，再决定是否清除手动版本。回退旧代码时，新状态键被忽略；手动版本及原有同步版本保持兼容。本次贡献不自动部署生产。

官方依据：[额度响应头及限制](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)、[限流后的等待与退避](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#handle-rate-limit-errors-appropriately)。这些规则要求不早于指定期限请求；在期限之后安排有界恢复检查是本项目的调度设计，不是 GitHub 要求必须立即重试。
