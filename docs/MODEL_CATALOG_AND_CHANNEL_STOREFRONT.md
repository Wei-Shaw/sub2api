# 模型目录、价格底稿与渠道货架

本文是 TokenSupply fork 后续「新模型适配 / 定价 / 对外货架」改造的计划。开发、审计、发布仍遵守 `docs/FORK_OPERATIONS_SOP.md`。

## 1. 要解决什么

现在加一个同类新模型，要改默认映射、多个平台的默认列表、计费兜底、打包价表，上线后再手改分组展示和渠道价目。还容易误以为必须等 Wei-Shaw 上游先适配。

真正该分开的是两件事：

- 协议没变，只是新模型名：不该等上游，也不该改一堆 Go 文件。
- 真的是新接口、新参数、新计费方式：写在自己 fork 里，不必等上游。

## 2. 已定产品规则

1. 用户能看见、能调用的模型，只由渠道决定。
2. 价格底稿由本 fork 自己维护。
3. 分组和账号不再限制模型。账号映射、渠道映射只负责改名。
4. Anthropic、OpenAI、Gemini、Antigravity、Grok、以及走这些通道的兼容模型，同一套规则。
5. Antigravity 的 `low` / `medium` / `high` / `tiered` 是上游真模型名，按真模型对待，不是本地假别名。
6. 没绑渠道的分组不当对外货架。对外卖的分组必须绑渠道。

## 3. 以后各层干什么

| 层 | 以后只干什么 | 不再干什么 |
|---|---|---|
| 渠道 | 对外货架：勾选可卖模型、改价、必要时改名 | 手打一长串模型名当唯一维护方式 |
| 本仓库模型目录 | 我们知道的模型、档位、默认改名、底稿价 | 把名单散落在多个 Go 文件里 |
| 上游同步 | 记录每个账号最近真正有的模型，给调度和渠道勾选参考 | 直接当用户货架 |
| 账号映射 | 把请求名改成上游名 | 当白名单 |
| 分组自定义模型列表 | 下线 | 再维护一套用户可见名单 |
| 分组定价 | 后续改成停用，或只做渠道价上的加价 | 再当第三套价表 |
| Wei-Shaw / LiteLLM 远程价 | 只当「发现新官方模型」的输入 | 运行时主价格源 |

Composite 分组没有自己的模型目录。它只是按请求把流量分到上面这些具体平台；货架和价格仍按落地主平台的渠道配置走。

## 4. 覆盖的平台

### Antigravity

- 上游会直接返回并接受 `gemini-3.6-flash-high` 这类档位名。
- 生产上 `gemini-3.6-flash` → `gemini-3.6-flash-tiered` 只是渠道默认简称，不是因为 `-tiered` 是假的。
- `gemini-3.1-pro-high` → `gemini-pro-agent` 这类改名继续留在目录里。
- 新 Flash 档位：同步上来后，渠道勾选即可。价格跟基座模型。

### Gemini

- 官方 API 通常只有基座名，没有 Antigravity 那套后缀档位。
- 目录里同一基座可以同时挂 `gemini` 和 `antigravity`，但档位别名只标在 Antigravity。

### OpenAI

- 默认列表、Codex 别名、`gpt-5.6` → `gpt-5.6-sol` 这类拼写归一，逐步收进目录。
- 空映射的 OAuth 账号现在还有一层「别的厂的模型不要往 Codex 上打」。这是防 400，不是货架。渠道货架做完后，再决定它还留不留。

### Anthropic

- Claude 系列底稿价、日期后缀、旧名迁新名收进目录。
- 不再靠代码里一长串 `Contains("opus")` 当唯一价格来源；目录精确名优先。

### Grok

- 现有默认映射和底稿价收进目录。
- 上游模型列表同步后，渠道勾选，不再先改 `xai` 默认表。

### 兼容模型（DeepSeek / GLM / Kimi / MiniMax 等）

- 它们通常走 OpenAI 兼容通道，不单独占一个 platform 枚举。
- 底稿价仍放在同一份目录里，平台标记为实际承载通道，例如 `openai`。
- 未知名字继续不乱猜价。

## 5. 分步

一步一个功能 PR。功能 PR 不改版本号、不打 tag、不部署。

### 第 1 步：模型目录和价格底稿（本 PR）

- 在仓库里放一份自己的目录和底稿价。
- 运行时：渠道价 > 分组价（本步暂不删）> 目录锁定价（只覆盖目录里写了的字段）> 远程/打包 LiteLLM > 旧硬编码兜底 > 目录未锁定价（只补两边都没有的新模型）。
- 默认不整卡覆盖 LiteLLM / 硬编码兜底。现网已卖模型的价格保持原样。
- 只有 thinking 档位（`-high` / `-low` / `-medium` / `-tiered`）才跟基座共用价卡。商业别名不能绑到另一个已卖模型上。
- 把 Gemini 3.7 Flash 的底稿价和档位写进目录，但本步不改默认映射、不改分组、不改渠道，所以现网还卖不了 3.7。
- 自动化暂不做。先把人维护的底稿立住。

验收：加一个已有协议的新模型，以后理论上只改目录就能有价；现有已卖模型的底稿价不变。

### 第 2 步：渠道变成货架

- 渠道定价页改成从目录 + 最近同步到的上游模型里勾选。
- 显示覆盖率，例如 `8/10 账号有`。不要只用「所有上游都有」当唯一可选列表。
- 勾上后自动带目录价，允许改。
- 绑了渠道的分组，`/v1/models` 和真实请求都只认渠道勾过的模型。
- 新渠道默认打开模型限制。旧渠道不自动翻开关。

### 第 3 步：账号映射只改名

- 新账号默认不再靠映射当白名单。
- 旧账号的白名单不自动拆，避免突然放行以前故意藏起来的模型。
- `/v1/models` 不再从账号映射 key 的并集推断。

### 第 4 步：定时同步上游能力

- 定时拉取各账号真正有的模型，只保存上次成功结果。
- 某次拉取失败，沿用旧结果，不把货架或候选列表收缩成空。
- 调度时只打给当前能接的账号。
- 这份列表不当用户货架。

### 第 5 步：收尾

- 下线分组自定义模型列表。
- 分组定价改为停用，或只做加价。
- 默认映射、默认列表尽量改成读目录，删掉重复手写名单。
- 再补「发现新官方模型」的草稿 PR 自动化。自动化不得覆盖人手锁定的价格。

## 6. 还需要写代码的情况

下面这些仍然要开功能 PR，不能只改目录：

- 新平台或新认证方式
- 新请求/响应协议，或新的思考/工具参数
- 新的计费方式，例如按次、按图片、按视频秒数
- 安全、调度、限流语义变化

## 7. 明确不做

- 不用「所有上游的最大公因」当用户可见/可调用列表。
- 不把这次重构跟已关闭的 Gemini 3.7 单独适配 PR 揉在一起。
- 不在功能 PR 里改 `VERSION`、打 tag、部署生产。
- 不把生产地址、密钥、用户数据写进仓库。
- 不擅自改现网已在卖的价格，例如 Gemini 3.6 Flash 现网仍按 `$1.50 / $7.50 / $0.15`。
- 不为了少冲突去干等 Wei-Shaw。

## 8. 现网迁移注意

当前生产对外卖模型，主要靠「分组展示列表 + 渠道限制 + 渠道价目 + 账号映射」。在第 2 步上线前，这套继续生效。

第 2 步上线时必须保证：

- 蓝绿期间新旧版本能共存。
- 已经绑渠道并打开限制的分组，用户看到的模型不能无故变少或变多。
- 没绑渠道的分组行为要写进该 PR 的范围说明。
