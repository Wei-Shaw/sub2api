# 上游账单对账

“我的账户 → 上游对账”读取供应商官方成本数据，保存独立的账单与分摊记录。“使用记录”页面同时显示对应整月的上游分摊成本摘要。

使用记录中的上游摘要不随该页的用户、分组或 Key 筛选变化：管理员看到全站整月汇总，普通用户看到本人所有虚拟 Key 的整月汇总；具体分摊请进入上游对账查看。

此功能不修改 `usage_logs` 的请求费用，不扣减或返还用户余额，不调整订阅或平台配额。原系统的 `actual_cost` 仍然表示本站规则计算的扣费，不是供应商发票金额。

管理员可切换三个面板：

- **原始供应商账单**：供应商成本条目、账期、币种、原始精度金额，以及按需读取的原始 API 行数据。原始行不包含本系统发送的凭据或授权头。
- **对齐后的本站账单**：依据资源绑定和本站使用记录，细分至上游账号、用户和虚拟 Key，展示分配方式和未分配成本。
- **用量核对与差异**：展示官方 Token 证据、可对齐的本地用量及差额。没有可靠用量接口、字段口径不同或无法核实时显示相应状态，不填造一个零值。

普通用户只能查看自己的对齐结果。原始行通过独立的管理员接口按需读取，不随每次列表/使用记录摘要传输；原始读取也进入操作审计。

## 首批供应商

| 供应商 | 授权 | 官方数据范围 | 成本口径与限制 |
| --- | --- | --- | --- |

| 腾讯混元 | 国内站 CAM SecretId / SecretKey，混元产品 BusinessCode | `DescribeBillDetail` 产品账单，按 ResourceId 绑定；北京时间整月 | 组件 `RealCost` 合计，折后成本，CNY；不是账户余额，也不等同于现金支付额；暂不支持国际站 |
| Anthropic Claude | 组织 Admin API Key；可选 Workspace ID | Cost API，UTC 日成本、工作区和费用说明 | 官方返回的美分精确换算为 USD；本日尚未结束的成本不拉取；非模型调用 Key 账单 |
| 阿里云百炼 / Qwen | RAM AccessKey ID / Secret；资源归属 Account ID 与产品编码 | `DescribeInstanceBill`，资源归属账号及产品、月度计费项 | 官方应付金额 `PretaxAmount`，保留币种；不是单个百炼模型 Key 的账单 |
| 火山引擎方舟 / 豆包 | 子用户 AccessKey ID / Secret；资源归属 Account ID 与产品编码 | `ListBillDetail`，资源归属账号及产品、月度账单明细 | 官方应付金额 `PayableAmount`，保留币种；不是逐模型调用 Key 的账单 |

均非实时接口。本月数据可能延迟、为空或被供应商修订。这里保存的是官方成本 API 数据，不是下载供应商的 PDF 发票。供应商没有明确提供逐 API Key 账单时，界面不会把分摊称为逐 Key 实扣。

DeepSeek、Kimi 等余额查询没有加入历史对账：余额快照无法可靠还原每笔成本、退款及优惠。新增供应商需要有可验证的历史成本接口，不能仅凭余额变化冒充账单。

Qwen 是模型系列，不单独虚构一个计费平台：从阿里云百炼调用 Qwen 时使用 `aliyun`，通过其他云厂商调用时应接入实际出账平台。阿里云、火山引擎填写的是云平台专用账单读取授权，不是 DashScope / 方舟推理 API Key；产品编码应从实际费用中心确认，不根据“Qwen”“豆包”等模型名称猜测。两者都核对返回账单的资源归属账号，付款账号在多账号代付场景下可以不同。

## 配置流程

1. 在服务端设置固定的 `TOTP_ENCRYPTION_KEY`：32 字节随机值的 64 位十六进制字符串。该密钥复用现有 AES-256-GCM 加密设施。未固定配置时，系统拒绝保存或使用账单凭据。
2. 用管理员身份打开“我的账户 → 上游对账”，添加供应商连接。只填写平台 API 授权，不填写个人登录密码。普通用户只读自己的虚拟 Key 分摊，不能读取连接、上游账号或全站账单。
3. Azure 为服务主体在相应订阅授予 `Cost Management Reader`，并根据组织的计费账户类型确认成本可见权限。填写资源的完整 ARM ID，例如 `/subscriptions/<subscription-id>/resourceGroups/<group>/providers/Microsoft.CognitiveServices/accounts/<resource>`。仅拥有模型 `api-key` 不足以读成本。
4. 腾讯使用具备 `billing:DescribeBillDetail` 读取权限的 CAM 凭据。混元 `BusinessCode` 应从腾讯云实际产品账单或 `DescribeBillSummaryByProduct` 返回值确认，不能用模型名称猜测。后者若用于人工发现产品，需要另行授予其读取权限。
5. Anthropic 使用具有组织账单读取能力的 Admin API Key。不要把它用作模型调用 Key；妥善控制其权限。可限定工作区；留空会拉取各工作区。返回资源 `__organization__` 代表没有工作区归属的费用，不是所有工作区的合计。
6. 先选择月份手动同步，查看官方明细中的资源 ID，再将其绑定到本站已有的 **API Key 类型上游账号**。同一资源可以绑定多个上游账号；每个上游账号只能属于一个账单连接。不需要填写下游虚拟 Key 的明文。
7. 保存绑定后重新同步该月份。系统自动从原始使用记录里的 `account_id`、`api_key_id`、`user_id` 建立分摊。历史记录缺少这些对应关系时，不会猜测归属。

同一个云计费范围只配置一个连接。系统会阻止可识别的重复范围和账号绑定；但同一腾讯云账户下不同 CAM 身份，或同一 Anthropic 组织的不同 Admin Key，不一定能仅由凭据确定是同一个账单主体。不要用不同授权重复导入同一份账单。也不要同时导入一个组织总范围和它的重叠子范围。

导入时还会检查不同连接中同一供应商、同一资源的重叠账期，发现重叠就拒绝第二份导入，不把费用再累加。空资源或 `__organization__` 等通用标识也按此保守处理：不同云主体若碰巧使用同样的通用标识，可能被拒绝，不能把这种冲突当作两个账号确实相同的证明；首版不支持无稳定资源身份的多主体重叠导入。

阿里云与火山引擎有显式且经返回数据核验的资源归属 Account ID，重复范围使用“供应商 + 归属账号 + 产品编码”识别，不因轮换 AccessKey 改变；这两者的同资源重叠检查还限定同一归属账号，允许不同已知账号拥有同名资源。其他供应商仍采用上述保守规则。

为防止历史账单被重新归到另一个主体，阿里云与火山连接创建后的归属 Account ID 和产品编码不可更改；更换账号或产品请新建连接。凭据轮换、同步周期、回溯范围、分摊策略和资源绑定仍可编辑。

## 界面可配置项与筛选

| 配置 | 默认值 | 行为 |
| --- | --- | --- |
| 自动同步间隔 | 24 小时 | 1–168 小时；后台按小时检查到期任务，不代表供应商实时出账 |
| 自动回溯月份 | 2 | 1–6 个月，包含本月，优先同步最近月份；更早账期可手动同步 |
| 分摊策略 | `local_weighted` | 有可靠官方计量时优先使用；其余成本按本站用量权重估算 |
| 仅可靠官方计量 | `official_only` | 缺少可验证的官方计量或本地用量超出官方时，保留为未分摊，不回退为全额估算 |
| 仅同步原始账单 | `disabled` | 不向虚拟 Key 分摊，不做本地 Token 核对；完整官方金额保留为未分摊 |

变更分摊策略或绑定后，重新同步对应月份才会更新该月结果。新策略记录在成功快照中；旧快照保留，余额和原请求扣费仍不变。旧客户端更新连接而未传新字段时，保留既有回溯月份和分摊策略，避免意外恢复估算。

无论哪一种策略，当官方和本地已具有可比口径，但本地用量反而超过官方时，都保留为未分摊并显示冲突，不再把整条官方费用回退为本站全额估算。

三个面板支持按供应商、连接、资源、核对状态及分摊状态筛选。原始账单逐条显示已分摊和未分摊金额，包括负数退款和小额尾差；筛选结果不改变整月汇总卡片。费用条目中的请求数与 Token 仅是该项的分摊权重，不应跨费项累加当作整月调用总量。

## 分摊规则

- 每条官方成本记录按其资源、币种和时间区间匹配上游账号的本地用量。
- 以下本地权重回退仅适用于默认 `local_weighted` 策略；严格或仅原始账单策略按上一节处理。
- 优先以 `usage_logs.total_cost` 的非负值为比例权重。该值是本站定价的 USD 参考权重，不是供应商币种的真实成本。
- 全部本地成本权重为零时，改用本地 Token 数；无可用权重或无绑定的账单保留为“未匹配 / 未分摊”。
- 依次细分到上游账号、用户、虚拟 Key。标注“按本地计费权重分摊”或“按 Token 权重分摊”，不宣称供应商直接返回了这些 Key 的实扣。
- 每条账单使用十进制定点分摊，分摊精度为 8 位小数，保留供应商原始金额字符串；尾差按最大余数法分配。负数调整/退款保留负号。每个币种分别满足：官方成本 = 已分摊成本 + 未分摊成本。不自动换汇。
- 一个资源的不同费用条目可能引用同一组请求和 Token 权重；表格中的权重不应跨费用条目累加作为总用量。

上游资源如果同时被其他系统使用，云账单也会包含站外调用。系统无法自动识别这部分成本，不会凭空计算一个“准确的站外差额”。需要只绑定专用资源，或在分析时考虑站外调用、折扣、预付/承诺消费和税费影响。模型价格不同也可能影响本地权重与供应商实际成本的比例。

## 官方 Token 核对

Anthropic 的 `/v1/organizations/usage_report/messages` 提供独立的官方用量。系统按工作区、UTC 日、模型、输入/输出/缓存类型、上下文区间、服务等级和地域，尝试关联对应的成本条目。只有完整读取并且各维度都一致，才能构成该费用条目的官方计量分母。首次同步没有可用官方用量时，仍可保存成本账单并标为无法核对。如果同一条账单以前已有官方计量对齐结果，而本次官方用量临时无法取得，则保留上次成功月份快照并重试，避免仅因网络故障把已核对的本站份额改回全额估算。

本地历史记录也有边界：本站强制缓存计费可能把输入 Token 改记为缓存读取，缓存 TTL 规则可能重新分类缓存写入，而旧记录不总是保留变更前的计量。因此首版**不使用历史输入/缓存类别自动进行官方比例计价**。地理计费维度等无法从本地记录验证时也不自动使用。

当前只对口径可验证的 Anthropic 输出 Token 条目启用官方计量分配：标准服务、无地域计费维度、可匹配的模型与上下文区间，且本地匹配用量不超过官方用量。分配计算为：该官方成本条目 × 当前 Key 的匹配输出 Token ÷ 该条目的官方输出 Token。未被本站解释的份额保留为未匹配成本，不能断言全部来自站外调用；账期延迟和缺失本地记录也可能形成差异。

其他条目仍按明确标注的本地权重估算，官方证据只用于展示或提示差异。即使使用官方 Token 分配，也不宣称已取得供应商逐请求或逐虚拟 Key 的独立发票。

Azure 本期 Cost Management 接口没有直接返回可用于此口径的 Token 数；Azure Monitor 的输入/输出 Token 是监控指标，不应直接等同可计费 Token。腾讯原始账单中的 `UsedAmount` / `UsedAmountUnit` / `RealTotalMeasure` 会留在原始明细：产品单位及资源包扣除前后口径不同，不能未经核实就按 Token 解释。本期不据此自动进行 Token 比例计价。

## 定时同步与数据安全

- 连接可设置 1–168 小时同步间隔，建议 24 小时。后台按小时检查到期连接，默认同步本月及上月，也可配置包含本月的最近 1–6 个月；更早月份可手动重拉。最近月份优先，避免旧账单先阻塞新账。
- 多进程/多实例通过 PostgreSQL 会话级 advisory lock 防止同一连接并发同步；编辑连接也使用相同锁空间。后台支持关闭取消，每个月同步上限 150 秒，自动回溯最多 6 个月有 15 分钟总预算；手动同步仍只针对单月。
- 一个月的完整分页读取、校验和分摊成功后，事务才切换该月的有效快照。任何分页、授权、网络或持久化失败不会替换该月最后成功的数据。自动任务可能只完成部分月份，此时分别保留各月最后成功结果。
- 相同内容重拉不重复累计。变化生成新的不可变版本，包括官方金额、原始精度金额、资源绑定及分摊输入；当前页面读取每月最新成功版本。历史版本保存在数据库，首版没有历史版本切换界面。
- 分摊随成功同步保存，因此随后清理用量或删除 Key 不会直接删除既有分摊。对于清理后重拉，会尽量保留先前的完整权重快照；清理发生在首次同步前，或账单资源/时间窗口变化，无法恢复未保留的历史用量。建议用量保留期至少覆盖需要对账的月份，先对账再清理。
- 凭据只以加密密文入库。读取连接只返回配置和“已保存”状态，不返回明文或密文。编辑时密码框留空保留原值。敏感保存请求的整个请求体被排除出审计日志；同步错误不包含授权头或供应商响应正文。
- 使用固定官方 HTTPS 域名，禁止跟随重定向；限制分页、响应大小和重试，避免把凭据发送到任意配置地址。
- 备份数据库时需要包含新增的 `upstream_billing_*` 表，并将加密密钥在安全位置单独备份。丢失原密钥无法解密已有授权；可恢复原密钥，或重新填写完整授权。不要为启用此功能而随意替换已用于 TOTP/其他加密数据的密钥。
- 暂不提供删除账单连接的按钮；可暂停自动同步，避免误删财务历史。

## 后端与扩展

所有接口均需有效用户登录。`GET /api/v1/upstream-billing/report?month=YYYY-MM` 对普通用户强制采用会话身份过滤，忽略调用者自报的用户或管理员身份。管理员可调用连接列表、API Key 上游账号选项、创建/更新和手动同步接口。

使用记录摘要调用 `/api/v1/upstream-billing/summary?month=YYYY-MM`，只聚合各币种成本；原始 API 行通过 `/api/v1/upstream-billing/bills/:id/source` 按需读取，后者仅管理员可用。

数据库迁移 `239_upstream_reconciliation.sql` 自动创建独立表，不改写原收费表。适配器实现位于 `backend/internal/service/upstream_billing_providers.go`；新增供应商需要同时定义配置白名单、授权方式、账期时区、原始币种、精度、分页规则和稳定账单标识，并补充固定响应测试和前端字段说明。只有余额接口的供应商应作为余额监控单独实现。

迁移 `240_upstream_reconciliation_policy.sql` 增加回溯月份、连接分摊策略与快照策略字段，未修改已存在的 239 迁移内容。升级时先让系统正常执行迁移，再使用新界面或接口。

## 管理员原始账单 API

供受信任的后台对账系统调用，不需要向下游传递任何云供应商凭据。全部为只读接口，并使用现有管理员认证：请求头 `x-api-key: <sub2api 管理员 API Key>`，或 `Authorization: Bearer <管理员 JWT>`。普通用户 JWT 和模型调用虚拟 Key 不可读取。现有管理员 API Key 具有较广的管理权限，不能直接发给普通客户，也不要放在浏览器公开代码或 URL 参数中。

| 路径 | 用途 |
| --- | --- |
| `GET /api/v1/admin/upstream-billing/capabilities` | 查询支持的供应商、历史账单能力、过滤参数、认证方式与分页限制；DeepSeek 明确返回不支持历史账单 |
| `GET /api/v1/admin/upstream-billing/bills` | 分页读取各连接最新成功月份快照中的原始账单行 |
| `GET /api/v1/admin/upstream-billing/bills/:id` | 按本系统账单数字 ID 读取单条成功快照，包括列表固定的历史版本 |

列表和单条读取都必须提供 `month=YYYY-MM`，可选 `connection_id`、`provider`、`resource_id` 精确过滤。列表另支持 `limit`（默认 10，最大 20）和 `cursor`。管理员路由同样进行限流、`Cache-Control: no-store` 和敏感读取审计，不把原始响应或授权凭据写进访问审计。

示例请求（认证只放请求头）：

```http
GET /api/v1/admin/upstream-billing/bills?month=2026-09&provider=aliyun&connection_id=12&limit=10
x-api-key: <SUB2API_ADMIN_API_KEY>
```

响应遵循现有 `{ "code": 0, "data": ... }` 封装，`data` 含 `month`、`snapshot_at`、`items`、`limit`、`has_more`、`next_cursor`。每条包含本系统 `id` / `run_id`、供应商 `provider_bill_id`、连接与资源标识、账期、币种、原始精度 `source_amount`、分摊精度 `amount`、同步时间、快照分摊策略，以及完整 `raw_source` 和可用的 Token 核对证据；不返回连接配置或密钥。

客户端应按 `has_more` 和 `next_cursor` 继续，并保留原月份及过滤条件。首屏固定成功快照集合，后续分页即使发生新同步也不会混入新版本；想读取更新后的账单，请重新不带游标请求首屏。每页有 2 MiB 上限，可能少于 `limit`，不能仅凭条数判断是否读完。金额为十进制字符串，应使用十进制定点计算，不通过浮点数汇总，也不要跨币种相加。

原始账单是官方成本 API 的原始条目，不是发票 PDF；接口不即时请求云平台，而是读取 sub2api 已成功同步保存的数据。

上线前使用真实只读授权验证：与供应商控制台同资源、同账期、同币种、同税费口径比较；核对负数修订、优惠和延迟入账。仓库测试使用模拟响应，不代表已验证任何真实云账户的权限或账单。
