# 单用户风控处罚范围

**本地实现与验收记录 · 2026 年 11 月 24 日**

管理员可以为单个普通用户选择「仅禁用涉事 Key」。这里的 Key 指该用户调用平台时使用的 API Key。

## 一、管理员设置与业务规则

入口为「用户管理 → 编辑用户 → 风控处罚范围」。已有用户和新注册用户默认选择「禁用用户」。修改其他资料时，管理界面只提交实际改动的字段。

| 设置 | 同一统计窗口内的计数对象 | 达到现有阈值后的行为 |
| --- | --- | --- |
| 禁用用户（默认） | 同一用户所有 Key 的有效命中合计 | 禁用账户。该用户的 API Key、已有登录会话和新登录均被拒绝。 |
| 仅禁用涉事 Key · 长期（默认） | 每把 Key 单独累计 | 锁定达阈值的 Key，由管理员解锁。用户仍可登录并使用其他可用 Key。 |
| 仅禁用涉事 Key · 限时 | 每把 Key 单独累计 | 从这把 Key 实际被锁定时开始计时，到期自动解除风控锁。选择限时时默认 10 分钟，管理员可输入其他正整数分钟，也可提前解锁。 |

例如，02:00 达到阈值并被锁定，时长为 10 分钟，02:10 起可再次通过风控鉴权。锁定期间再次命中不会续期。修改用户的禁用时长只影响下一次锁定，当前锁沿用触发时的时长。切回「禁用用户」会清除该时长偏好，下次选择「仅禁用涉事 Key」时预选长期。

例如将测试阈值设为 2。试点用户的 K1、K2 各命中一次，两把 Key 仍可用。K1 再命中一次，只有 K1 被锁。默认用户的两把 Key 各命中一次，账户即被禁用。实际阈值、窗口、全局自动处罚开关均取自现有风控配置。

当次请求仍执行配置的检测、拦截和会话屏蔽规则。可信用户的审计、管理员保护、重复哈希排除，以及上游 `cyber_policy` 是否计入阈值，均沿用各自规则。

## 二、数据与接口约定

| 位置 | 已实现的行为 |
| --- | --- |
| `users` | `moderation_penalty_scope` 允许 `user` 或 `api_key`，数据库默认 `user`。仅在实际切换策略时更新 `moderation_scope_changed_at`，以此开始新一轮计数。 |
| `api_keys` | `moderation_locked_at` 记录起锁时间，`moderation_locked_until` 存储限时锁的截止时间，长期锁此字段为空。计数和鉴权采用实际解锁时刻（手动解锁时间或自然到期时间）。手动停用、到期、额度耗尽等限制在解锁后仍各自生效。 |
| `content_moderation_logs` | 新事件记录服务端事件 ID、发生时间、计数范围和实际处罚。`penalty_locked_until` 保留本次限时处罚原定的截止时间，供日志和锁定通知使用。`auto_banned` 仍表示禁用用户。旧日志按原封号边界参与默认用户的计数。 |
| `PUT /api/v1/admin/users/:id` | 可分别提交 `moderation_penalty_scope` 和 `moderation_key_lock_minutes`。时长 `0` 表示长期，`1` 到 `2147483647` 表示分钟，正数只适用于 Key 范围。单独修改资料保留既有偏好。非法值返回 `400`，普通用户通过自助资料接口设置处罚参数返回 `403`。 |
| `POST /api/v1/admin/risk-control/users/:user_id/api-keys/:key_id/unlock` | 校验管理权限与 Key 归属。重复操作成功返回 `unlocked: false`，保留上次实际解锁时间。`moderation_admin_actions` 用操作人、用户和 Key 的 ID 记录策略修改和解锁结果。 |

切换处罚范围后，按新范围统计随后发生的事件。现有长期锁由管理员解除，限时锁继续按原截止时间解除。解锁单把 Key 只重开该 Key 的计数周期，其他 Key 的计数和历史日志继续保留。

## 三、后端实现

1. 普通审核和可计数的上游安全事件共用 `RecordHit`。PostgreSQL 在同一事务中锁定用户和归属 Key，按事件 ID 去重，写入命中，再按生效范围、发生时间和窗口计数。达到阈值时，处罚和日志一起提交。缺少有效归属或早于策略切换、解锁边界的事件只记录审计。
2. 默认用户合并同一用户各 Key 的命中，并使用最近一次用户自动封禁作为计数边界。Key 策略按 `(user_id, api_key_id)` 计数。事务提交后才触发缓存失效和通知，单 Key 处罚只清理对应凭证。风控日志和处罚邮件分别标明「已禁用用户」或「已锁定 Key」。
3. 标准 HTTP、Google 兼容入口优先检验风控锁。命中认证缓存或复用其他请求的在途凭证查询结果时，按主键向数据库核对锁、最近解锁时间和用户状态。解锁时间变化时重新取完整鉴权信息，包含普通停用、到期、额度和 IP 限制。权威查询失败时拒绝放行。
4. WebSocket 在握手和后续请求转发前执行检查。连接空闲期间若经历一次锁定和解锁，下一轮要求重新连接，以便按当前权限重新握手。已经转发的请求可以结束。
5. PostgreSQL 按当前语句的数据库时间判断风控锁，到期即生效，无需定时任务。即使服务离线跨过截止时间，恢复后的首次鉴权也按该截止时间重开计数周期和刷新权限。锁定期内发生的延迟事件和重投事件不会计入下一轮。
6. 用户无法自行启用或删除被风控锁定的凭证。管理员可从用户的 Key 列表或风险控制日志执行「解锁此 Key」。原有「解封用户」操作只用于账户处罚。

## 四、本地验收与发布顺序

本地 PostgreSQL 18 和 Redis 8.4 上的 8 组业务集成测试连续运行两轮。网关和权限检查使用真实数据库、Redis、鉴权中间件及本地测试请求。

| 场景 | 验收结果 |
| --- | --- |
| 双用户、两把 Key、阈值 2 | 试点用户 K1 返回 `401 API_KEY_DISABLED`，K2 可用，新登录及已有会话成功。默认用户 B 两把 Key 均返回 `401 USER_INACTIVE`，已有会话和新登录均被拒绝。普通审核和上游事件均参与对照。 |
| 管理权限与恢复 | 普通用户设置策略或访问解锁接口得到 `403`，管理员操作归属不匹配的 Key 得到 `404`。切换策略保留已有锁，重复保存与重复解锁均保留计数边界。 |
| 并发、重投与历史数据 | 两个实例同时记录与重投相同事件，并发计费后得到两条命中、一次加锁及正确计费。并发切换策略、解锁与延迟事件的结果符合数据库提交顺序。默认用户旧日志、上次封号边界及历史处罚展示通过。 |
| 排除与保护 | 自动处罚关闭、管理员保护、可信审计、重复哈希、排除上游事件、过窗口及归属无效均按配置执行。 |
| 缓存和已有连接 | 预热缓存后，即使失效消息丢失，HTTP 和 Google 入口也会拒绝被锁 Key。自动到期或管理员提前解锁后，标准 HTTP 分别按手动停用、到期、额度耗尽返回 `401`、`403`、`429`。两种 WebSocket 转发模式的单元测试覆盖后续轮次拦截及重新握手。 |
| 限时锁 | 验证 10 分钟和自定义 37 分钟、正在生效的锁不续期、提前解锁、自然到期后的再次计数和再次锁定、历史截止时间以及释放后的删除。HTTP、Google 入口都覆盖有旧缓存时到期恢复。 |
| 前端 | 用户编辑、管理员 Key 列表、风控日志、个人 Key 列表共 65 项测试通过，另有 3 项中英文翻译校验。覆盖默认时长、输入校验、独立配置，以及停留在列表时到期重新读取服务端状态。TypeScript 类型检查通过。 |

Go 功能专项测试通过。用量分页契约已覆盖 `first_visible_text_ms`，`TestAPIContracts` 复测通过。Ollama 限流回调测试 `TestOllamaProbeCallback_StaleLongDoesNotOverrideNewShort` 在本机 Windows 环境复测失败，在同一环境下对官方 `0f6671457` 单独运行 5 次也均复现。

交付范围为本地开发和功能验收。发布时按顺序应用 `253_moderation_penalty_scope.sql`、`254_moderation_penalty_indexes_notx.sql` 和 `255_moderation_key_lock_duration.sql`。已运行前两个迁移的环境只需新增 `255`。第二个迁移在事务外并发构建风控日志索引，避免持有字段迁移的锁等待索引建成。第三个迁移为旧策略和已有锁保留长期语义。待所有网关实例升级、按生产流量评估新增主键查询的延迟与连接池占用后，再为选定用户开启。需要回滚到旧版时，应先逐一处理试点策略和现存的 Key 锁，确保线上凭证维持预期状态。
