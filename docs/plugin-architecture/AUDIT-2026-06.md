## 5. antigravity 回退修复进展（2026-06）

### 5.0 复核结论（live 路径取证）

真实流量路径：`GatewayHandler → GatewayPipeline.Execute → selectAndForward → PluginGatewayProvider.Forward（插件单次上游调用）→ doneToUpstreamError → handleForwardError → HandlePipelineUpstreamError`，成功则 `recordUsage`。逐项核对：

- **项 1（INTERNAL 500 渐进惩罚）— 确认缺失**。`isAntigravityInternalServerError` / `handleInternal500RetryExhausted` / `resetInternal500Counter` 仅被 bypass 的 `antigravity_gateway_service.go:773-805` 引用；`RateLimitService.HandleUpstreamError`（连同 `tryTempUnschedulable`）不含「连续整轮 INTERNAL 500 → 渐进惩罚」累计语义。插件 `gateway_upstream.go:handleErrorResponse` 对 500 只发结构化 `GatewayUpstreamError`（含 `status_code` + `response_body`），未做惩罚。**→ 已修复（5.1）**。
- **项 2（OAuth smart-retry，`antigravity_gateway_service.go:185-423`）— 确认缺失**。插件无 `parseAntigravitySmartRetryInfo` / model-capacity-exhausted / URL fallback 等逻辑；pipeline 对 429/503 仅走通用 failover。**→ 不盲改，方案见 5.3**。
- **项 3（单账号 in-place 重试，`:439-`，≤15s/累计≤30s/≤3 次/读 retry-after）— 确认被替换**。pipeline `pipeline_forward.go:18-21` 固定 `maxSameAccountRetries=3` × `sameAccountRetryDelay=500ms`，且仅当 `UpstreamFailoverError.RetryableOnSameAccount=true` 才触发；插件对 500/429 **未**设 `retry_on_same_account`，故 antigravity 实际走账号切换而非同账号重试。**→ 不盲改，方案见 5.3**。
- **项 4（AI Credits/overages，`antigravity_credits_overages.go`）— 确认缺失**。全部挂在 `*AntigravityGatewayService`，由 bypass 的 `antigravityRetryLoop` 调用；插件 Forward 无 `injectEnabledCreditTypes`。`manifest.go` 的 `supports_allow_overages` 位于 `FrontendMeta`，是**前端 UI 能力位**（驱动账号表单 overages 开关），与 host gateway capability 无关。`allow_overages` 写入 `account.Extra` 后仍被 `IsOveragesEnabled()` 在 quota-scope 解析与 admin 改值清 `AICredits` key 处读取，故开关并非完全无效，但**转发期 overages 注入确已丢失**。**→ 保守保留开关 + 加 TODO（5.2）**。

### 5.1 已做：INTERNAL 500 渐进惩罚复刻（host post-flight hook）

复用核心既有 penalty 算法，未重写。差异通过 hook 注入，pipeline 主流程保持平台无关（无 `switch platform`）。

- `backend/internal/service/antigravity_internal500_penalty.go`：新增最小接口 `Internal500PenaltyHook`（`PenalizeInternal500` / `ClearInternal500`）+ 导出判定 `IsAntigravityInternal500`；`*AntigravityGatewayService` 实现接口，内部委托既有私有方法 `handleInternal500RetryExhausted` / `resetInternal500Counter`（算法、redis 计数器、tier 常量 30min/2h/永久禁用全部不动）。magic message/status 仍由既有常量级 `isAntigravityInternalServerError` 承载。
- `backend/internal/service/gateway_service.go`：`GatewayService` 加 `internal500PenaltyHook`（`sync.RWMutex` 保护）。
- `backend/internal/service/gateway_error_handling.go`：`SetInternal500PenaltyHook` setter；`HandlePipelineUpstreamError` 末尾调 `applyInternal500PenaltyIfMatched`（平台 guard + INTERNAL 500 匹配后 `PenalizeInternal500`）；新增 `HandlePipelineForwardSuccess`（成功 reset 计数）。**平台 guard 落在 service 内部，不进 pipeline 主流程。**

### 5.3 待决策（不盲改，需人工/产品确认）

> 均涉及重试策略与产品取舍，且会改变 antigravity 的失败重试行为，故仅出方案、未实现。

**项 3 — 单账号 in-place 重试语义差异**

- 现状：`pipeline_forward.go:18-21`（`maxSameAccountRetries=3`、`sameAccountRetryDelay=500ms` 固定）；`handleSameAccountRetry`（`:376`）仅在 `failoverErr.RetryableOnSameAccount` 时触发。legacy `antigravity_gateway_service.go:439-` 为 ≤15s 单次 / 累计 ≤30s / ≤3 次，且读 `retry-after` 动态退避。
- 差异影响：① antigravity 的 500/429 当前未带 `retry_on_same_account`，根本不会进同账号重试，直接切号——与 legacy「先同账号退避重试再切」不同；② 即便进重试，固定 500ms 退避忽略上游 `retry-after`，与 legacy 的 retry-after 感知不一致。
- 方案选项：
  - **A（最小侵入）**：插件 `gateway_failover.go` 对特定瞬态（429 含 `retry-after`、Google 间歇性错误）设 `GatewayUpstreamError.retry_on_same_account=true`，并经 proto 既有 `response_headers` 透传 `retry-after`；host `handleSameAccountRetry` 改为读 `failoverErr.ResponseHeaders` 的 `retry-after` 决定退避（capped）。需在 host 侧把固定 `sameAccountRetryDelay` 改为「retry-after 优先、缺省 500ms」。
  - **B（保持现状）**：接受 pipeline 通用重试，仅补「读 retry-after」一处。
  - 风险：放宽同账号重试会增加单账号压力 / 请求堆积（legacy 有 ≤30s 累计上限保护，pipeline 当前无累计墙钟上限）。**需产品确认是否要恢复 legacy 的累计时长上限语义。**

**项 2 — OAuth smart-retry**

- 现状：`handleSmartRetry`（`:185-423`）整套（429/503 分类 → model-capacity-exhausted 切号信号 / URL fallback / 配额限流标记）在插件路径缺失；pipeline 对 429/503 走通用 failover + `HandleUpstreamError` 的 temp-unschedulable 规则。
- 方案要点：smart-retry 的「分类 + 切号 vs 重试」决策应在**插件侧** `classifyShouldFailover` / `handleErrorResponse` 产出结构化信号（如细分 `error_type=quota_exhausted|rate_limited`），host 据此走 failover 或 same-account；URL fallback 属插件内 upstream 选址，应在插件 `gateway_upstream.go` 内实现，不上浮 host。
- 风险：逻辑复杂、与计费/limiter 交叉（配额限流标记影响调度），**需人工逐分支比对 legacy `handleSmartRetry` 后再实现**；本轮不动。

## 7. 第二波 per-plugin 深挖（迁移保真度 · 5 agent）

首轮把四个网关**合并**分析、gateway-vs-核心 agent 主要深挖 antigravity。第二波对 openai/anthropic/gemini **逐插件**核查迁移保真度 + channel-management 第二角度（安全/并发）+ hello-world 参考质量。**核心结论：antigravity 的回退不是孤例——四个网关均存在程度不一的核心边界逻辑丢失，且存在一条跨平台共性回退。**

### 7.1 系统性回退模式（最重要）

网关抽取只把「happy-path 转发」搬进插件。**挂在各平台被旁路 service 上的平台专属边界逻辑被丢弃且未在插件/host 复刻；挂在共享 `RateLimitService` 上的则保留。** 这解释了为何 OpenAI 回退最轻（其 403/429/401/402 逻辑本就在共享服务）、antigravity/anthropic/gemini 回退较重（专属逻辑挂在各自 service）。

另有**计费漂移子模式**：proto `GatewayForwardResult` 缺字段，导致核心计费的若干细分项在 live 路径静默降级——antigravity（overages）、anthropic（1h cache→5m 价）、gemini（ImageCount 未设→不走每图价）三处同型。

### 7.2 🔴 跨平台共性回退（首轮 §1.1 漏记，影响全部 4 网关）

**model-not-found 按模型限流在 pipeline live 路径丢失**：`UpstreamFailoverError`（`backend/internal/service/gateway_service.go:468-474`）**结构体无 model 字段**，`HandlePipelineUpstreamError`（`gateway_error_handling.go:42-53`）调 `HandleUpstreamError` 不传 `requestedModel` → `HandleUpstreamModelNotFound`（`ratelimit_service.go:1646`）在 live 路径**永不触发**。某账号对某模型返回 model-not-found 时不再「仅冷却该模型」，退化为通用切号。`HandleUpstreamModelNotFound` 平台通用（显式处理 antigravity/mapped model），故 openai/anthropic/gemini/antigravity 全中。**修复小**：`UpstreamFailoverError` 加 `RequestedModel` 字段 + `HandlePipelineUpstreamError` 透传。
