# TokenSupply v0.1.166-ts.1

## Highlights

- Adds durable, policy-driven notification email delivery with retry, deduplication, delivery audit records, encrypted sensitive template variables, and administrator health visibility.
- Reworks operations alerting around service-quality signals, separating client-caused failures from provider and platform degradation before those failures affect SLA metrics or alerts.
- Advances the fork from the upstream 0.1.164 baseline to upstream 0.1.166, including gateway compatibility, security, rate-limit, billing, and mobile administration improvements.

## Fork Changes

- Centralizes business and operations email routing behind channel-level policy and recipient controls. Registration, password reset, balance, payment, refund, content moderation, scheduled report, and operations alert messages use the durable delivery path where applicable.
- Adds refund-request confirmation email policy, idempotent enqueueing, bounded retries, stale-lease recovery, terminal retention, redacted diagnostics, and encrypted storage for verification codes and reset links.
- Adds alert evaluation v2 with minimum sample and failure gates, recovery thresholds, sustained recovery, cooldown suppression, shadow mode, evaluation history, and explicit incident families.
- Adds versioned error classification for client, provider, platform, capacity, security, and compatibility outcomes. Client policy failures and cancellations no longer distort platform SLA calculations.
- Adds a repository SOP, PR contract, release-candidate validator, release-safety CI job, and versioned release notes read from the immutable tagged commit.

## Upstream Changes

- Baseline: upstream 0.1.164 to upstream 0.1.166, including the post-0.1.166 prompt-audit credential recovery fix.
- Adds panel API rate limiting, registration email-alias deduplication, ChatGPT Live gateway support, and further OpenAI Responses, Anthropic, Gemini, Grok, Ollama, and Antigravity compatibility fixes.
- Improves usage/session correlation, billing aggregation by currency, administrator filtering, channel availability on mobile layouts, and dependency security updates.
- Supports an explicit `CONFIG_FILE` source and adds `gateway.live.max_session_duration_seconds`, defaulting to 3600 seconds.

## Configuration And Migrations

- Applies migrations 188 through 196. They add the notification delivery queue, usage session identifiers, Live request typing, group Live permission, the registration alias index, alert evaluation state, encrypted email payload storage, error-classification metadata, and concurrent ops v2 indexes.
- The schema rollout is additive and reviewed for blue-green compatibility. Columns added to existing tables remain nullable for old-image writes; indexes on existing tables are created concurrently. Transactional migrations use a one-second lock timeout so a busy table fails the new instance quickly instead of queuing DDL ahead of live requests.
- No new mandatory environment variable is required. Existing SMTP configuration remains required for actual email delivery; disabled channels remain suppressed by policy.
- Administrators should review the new email notification recipients and operations alert rules after upgrade. Untouched legacy alert defaults are reconciled at read time only when every configurable field matches the historical fingerprint; any administrator change, including filters, is preserved.

## Deployment And Rollback

- Deploy only through the managed updater after confirming the database backup, current active digest, previous completion ledger, and healthy deployer state.
- A direct managed upgrade from `v0.1.164-ts.6` is supported. Keep the previous completed image available while migrations run and during the post-switch observation window.
- Migrations are compatible with the previous application image, so an image rollback to `v0.1.164-ts.6` remains available if the deployer completes its normal rollback checks. Do not roll back by editing Nginx, Compose, or deployer state manually.
- If migration startup reports a lock timeout, leave the serving slot unchanged and retry through the managed updater after the conflicting database transaction finishes.

## Verification

- Email delivery and operations alerting changes passed backend unit and integration tests, frontend lint, type checking, component tests, and an isolated amd64 Docker upgrade from `v0.1.164-ts.6` without an application, PostgreSQL, or Redis restart.
- Rollback compatibility passed the migration history gate from every completed fork release baseline. PostgreSQL 18 and Redis 8 integration tests covered nullable legacy rows, concurrent indexes, migration idempotency, and fail-fast lock contention while legacy writes remained available; an independent audit found no open P0/P1 issues.
- The upstream 0.1.166 synchronization passed backend unit tests, frontend lint, type checking, 1,346 Vitest tests, production frontend build, deployment script checks, and GitHub integration tests.
- The workflow standardization passed release candidate fixtures, release safety injection and delimiter tests, shell checks, frontend tests, Go lint, backend unit tests, and backend integration tests on GitHub Actions.

## Known Limitations

- Historical operations errors are not rewritten during deployment. Legacy business-limit rows retain their old SLA exclusion; other unclassified legacy failures remain conservative unknown SLA failures, so historical windows are not equivalent to precise v2 classification.
- Legacy alert reconciliation is read-time only until an administrator saves the effective rule. An image rollback can therefore temporarily restore the old alert semantics without affecting request service or data integrity.
- In an extreme rollback where the old aggregation worker restarts, it can transiently overwrite a v2 aggregate while leaving its version marker. A later v2 startup invalidates and rebuilds the most recent 48 hours; monitor aggregation freshness after rollback and re-upgrade.
- Email delivery still depends on the configured external SMTP service. Permanent SMTP failures are retained as failed delivery records after bounded retries instead of being treated as successful sends.
