# TokenSupply v0.1.166-ts.2

## Highlights

- Fixes the managed Docker update menu so a retained historical success cannot hide a newer available release or its update button.
- Keeps the short completion confirmation for an update started by the current page, then returns to version-driven status after the automatic refresh.

## Fork Changes

- Treats the deployer's indefinitely retained successful terminal job as history after a page load. The current and latest version response now determines whether the administrator sees "up to date" or an available update.
- Continues to recover running deployments and failed, degraded, or rollback-failed states across refreshes so progress and actionable failures remain visible.
- Adds regression coverage for the production `v0.1.164-ts.6` to `v0.1.166-ts.1` display failure, historical update and rollback successes, the no-update state, and success completed by the current page poller.

## Upstream Changes

- Baseline remains upstream 0.1.166, including the post-0.1.166 prompt-audit credential recovery fix already included in `v0.1.166-ts.1`.
- No additional upstream commits are included in this hotfix release.

## Configuration And Migrations

- None. This release adds no database migration, setting, environment variable, API contract, or deployer protocol change.
- Blue-green coexistence with `v0.1.166-ts.1` and the currently deployed `v0.1.164-ts.6` remains compatible.

## Deployment And Rollback

- Publish and verify the immutable release completion ledger and image digest before production deployment.
- Because the currently deployed UI contains the bug fixed here, initiate the first upgrade to `v0.1.166-ts.2` through the managed deployer Unix socket with `expected_current_version` and a unique request ID. Do not patch the production frontend or deployer state manually.
- Keep the current `v0.1.164-ts.6` slot and the previous completed `v0.1.166-ts.1` image available during rollout. With no schema or configuration changes in this release, image rollback remains supported through the managed deployer.
- Observe active version, slot, upstream, digest, health, 5xx, latency, logs, and degraded state for at least five minutes after traffic switches.

## Verification

- The hotfix candidate passed focused managed-deployment Vitest coverage, TypeScript checking, ESLint, a full frontend test run of 1,348 tests, and a production frontend build.
- GitHub Actions passed backend unit and PostgreSQL/Redis integration tests, frontend checks, golangci-lint, shell/deployment contracts, and release-safety checks on the final hotfix SHA.
- Two-stage independent review rejected the first implementation for restoring successful jobs indefinitely, then approved the corrected final SHA with no open P0, P1, P2, or P3 findings.
- The separate Release PR must pass candidate validation and all required GitHub checks before the annotated tag is created.

## Known Limitations

- The existing production UI cannot be relied on to initiate this first upgrade because its historical completion state can cover the button. Use only the managed deployer socket for this transition.
- Success from a completed deployment is intentionally transient UI and is not restored after a later page load. Durable failure and degraded states continue to be restored.
