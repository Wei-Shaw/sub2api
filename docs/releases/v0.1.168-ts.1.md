# TokenSupply v0.1.168-ts.1

## Highlights

- Rebuilds managed Docker self-upgrades around one verified deployer binary shared by the release Bundle and application image, removing the split build paths that made the previous control-plane handoff unusable.
- Moves immutable tag creation behind a Build Once candidate: binaries, archives, Bundle, multi-architecture OCI image, checksums, and candidate manifest are built and audited before the promotion workflow may create the release tag.
- Adds durable control-plane staging, atomic activation and rollback, bounded retry, boot recovery, pending-state visibility, and deployment exclusion while an activation request remains unresolved.
- Includes upstream OpenAI Live session-store resilience, Claude Sonnet 5 status aliases, and quieter Passkey behavior when the feature is disabled.

## Fork Changes

- Gives the deployer an explicit release build identity while retaining the existing control protocol version as a separate compatibility field.
- Builds linux/amd64 and linux/arm64 deployer binaries once through GoReleaser. The OCI image and Bundle packaging consume those exact artifacts rather than recompiling them with different flags.
- Packages a root-owned control-plane manifest and deployer payload in the immutable application image. The running deployer resolves the target image digest, validates labels and manifest identity, extracts through a temporary container, verifies the architecture and SHA-256, and only then persists an activation request.
- Keeps the host activator intentionally small: it accepts only already verified staging files, creates the rollback binary atomically, swaps the deployer, restarts it, verifies the target build identity and active application, and restores the previous binary if health validation fails.
- Adds bounded timer retries, boot recovery, malformed-request quarantine, terminal cleanup recovery, and timeout decoration so the UI cannot remain pending forever after a damaged request or interrupted host activation.
- Recovers a successfully switched application deployment after a deployer restart by completing control-plane staging and scheduling activation. New update or rollback jobs return a conflict while an earlier activation request still exists.
- Makes the Bundle Installer preserve deployer service and upgrade timer existence, enabled state, and active state independently. Failed first-time bootstrap from a host without the timer restores Nginx and all host assets without falsely declaring rollback incomplete.
- Changes release preflight to push candidate image content by digest, verify the exact multi-architecture OCI payload and real Docker staging path, upload a recoverable candidate Artifact, and only then bind the immutable `candidate-<commit>` tag.
- Keeps the existing application update protocol label unchanged so the `v0.1.166-ts.4` deployer can validate the new application image after the required host bootstrap.

## Configuration And Migrations

- No database migrations are added after `v0.1.166-ts.4`.
- Managed hosts must install the new Bundle assets once before the first UI update from `v0.1.166-ts.4`. The installer deploys the new versioned deployer, stable activator, service unit, timer, tmpfiles policy, and managed upstream contract.
- Existing `UPDATE_MODE=docker-managed`, deployer socket, Compose, Nginx, and trusted-proxy settings remain in force. No new application environment variable is required.
- Source-built deployer installation remains disabled by default and requires an explicit development-only override; production bootstrap must use the checksummed release Bundle.

## Deployment And Rollback

- Production migration origin is `v0.1.166-ts.4`. Download and verify the `v0.1.168-ts.1` Bundle, back up PostgreSQL, record the active container ID/image digest/port and Nginx route, then run the Bundle Installer once while `v0.1.166-ts.4` continues serving traffic.
- Verify deployer health, socket access, timer state, managed upstream, and unchanged public application health before requesting the application update through the administrator UI.
- The application update remains blue-green. Keep the `v0.1.166-ts.4` container and image until the new slot, background runtime, public route, and control-plane status have remained healthy for at least five minutes.
- If application health, routing, drain, or background activation fails, the deployer restores the previous application slot. If control-plane activation fails after a successful application update, the application remains serving and the previous deployer binary is restored or the bounded recovery request remains visible for operator reconciliation.
- Application rollback to `v0.1.166-ts.4` is supported because this release adds no database migration. Application rollback does not downgrade the newer host control plane.

## Verification

- Local verification passed full backend unit tests, `go vet`, frontend lint and typecheck, 201 Vitest files with 1,388 tests, deployment asset and transaction suites, release safety and promotion contracts, Actionlint, and a GoReleaser v2.17.0 snapshot for linux/amd64 and linux/arm64.
- Installer tests cover first bootstrap, existing-install upgrade, exact service/timer state restoration, Nginx rollback, socket-directory preservation, and failure cases where a missing timer unit returns the same errors as real systemd.
- Activator tests cover atomic rollback-copy publication, process termination during mutation, idempotent success, bounded transient retry, permanent failure, health mismatch, rollback, and terminal cleanup recovery.
- Candidate tests verify shared deployer bytes across Bundle and OCI inputs, manifest/checksum identity, immutable digest matching, candidate Artifact recovery, tag-last ordering, and rejection of mismatched pre-existing tags.
- Independent deployment audit rejected the initial implementation for six recovery and release-order defects, then accepted the corrected control-plane design after the findings and first-bootstrap timer edge were closed.

This Release PR and its merged `main` SHA must independently pass the full release candidate workflow before promotion.

## Known Limitations

- The first migration from `v0.1.166-ts.4` cannot be completed solely from the web UI because that version's host helper cannot repair its own bootstrap assets. One reviewed Bundle Installer run is required; subsequent compatible releases are designed for UI-only managed updates.
- A defect in the currently running deployer's image extraction or staging path can still block it from preparing a future deployer and require another Bundle Installer. Real-Docker candidate gates reduce this residual bootstrap risk but cannot remove it structurally.
- Automatic retention of old Docker images is not included. Operators must monitor disk usage and retain the active image, rollback slot, running job references, and recent completed versions when cleaning unused images.
- Candidate image content is temporarily stored by digest before its immutable candidate tag is attached. External deletion during that interval causes the workflow to fail safely and requires rebuilding the candidate; it cannot publish different bytes under the audited release identity.
