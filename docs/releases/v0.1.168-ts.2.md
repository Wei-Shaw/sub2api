# TokenSupply v0.1.168-ts.2

## Highlights

- Adds server-side EasyPay reconciliation so a paid order can complete within the next scheduled pass even when the asynchronous callback never arrives and the user closes the payment page.
- Adds an administrator action to reject a pending refund request with a required reason, a durable audit record, and a policy-controlled notification to the user.

## Fork Changes

- Checks up to 50 unexpired `PENDING` EasyPay orders every 60 seconds. Paid results use the existing idempotent fulfillment transaction; unpaid results remain pending; network errors and ambiguous provider responses remain retryable.
- Rotates the reconciliation cursor between batches so a busy first page cannot permanently starve later orders, while the existing distributed leader lock ensures only one application instance polls during blue-green overlap.
- Requires the provider response to match the merchant ID, merchant order number, platform transaction number, and expected paid amount before crediting an order. A mismatch is rejected and recorded for review.
- Separates payment detection from successful recovery in the audit trail: `PAYMENT_DETECTED_BY_RECONCILE` records the provider observation, while `ORDER_RECOVERED_BY_RECONCILE` is written only after fulfillment commits.
- Keeps the existing EasyPay webhook, browser-return query, cancellation query, expiry query, and late-callback idempotency as independent recovery paths.
- Allows administrators to reject only orders currently in `REFUND_REQUESTED`. The rejection reason is required and limited to 1,000 Unicode characters; rejection restores the order to `COMPLETED` without calling the gateway or changing the user's balance.
- Writes `REFUND_REQUEST_REJECTED` in the same database transaction as the state change and sends the existing `billing.refund_rejected_user` notification according to the configured email policy.
- Gives each refund request generation an internal identity so a delayed approval or rejection cannot act on a newer refund request for the same order. Public API responses continue to expose the real user ID.
- Includes the release-workflow digest canonicalization corrections already merged after `v0.1.168-ts.1`; no deployer or activator behavior is changed in this release.

## Upstream Changes

- Baseline remains upstream `v0.1.168` at `5a6143097db142b72a6fc848c214e97214470bdd`; this release does not synchronize additional upstream commits.

## Configuration And Migrations

- Adds the administrator payment setting `EASYPAY_AUTO_RECONCILE_ENABLED`, exposed through `payment_easypay_auto_reconcile_enabled` and enabled by default.
- Disable this setting to stop scheduled EasyPay polling immediately if the provider throttles queries or returns unreliable data. Existing webhook and user-triggered query paths remain available.
- No database migration, order-table change, payment-amount change, recharge-multiplier change, or new environment variable is included.
- `v0.1.168-ts.1` and `v0.1.168-ts.2` remain schema-compatible during blue-green deployment.

## Deployment And Rollback

- Deploy through the managed administrator update flow after the Release workflow has published the immutable image and completion ledger. No Bundle Installer rerun is required when the host is already operating the `v0.1.168-ts.1` managed control plane.
- After switching traffic, verify public health, the active image digest, `degraded=false`, EasyPay query logs, reconciliation audit events, and refund-decision behavior. Then perform one minimal-value real EasyPay payment without relying on the callback or browser return to confirm end-to-end recovery.
- If only scheduled provider polling is unhealthy, turn off `EASYPAY_AUTO_RECONCILE_ENABLED` without rolling back the application. Otherwise the application can roll back to `v0.1.168-ts.1` because this release adds no migration or incompatible persisted format.
- Orders already fulfilled and refund requests already rejected are valid committed business records; an image rollback must not reverse those decisions.

## Known Limitations

- No real paid EasyPay query was executed during local or CI testing. The fake provider covers paid, unpaid, timeout, identity mismatch, amount mismatch, concurrent webhook, batch, and retry behavior; one minimal production canary remains required after deployment.
- Reconciliation intentionally processes at most 50 eligible orders per minute. A larger backlog is drained across later passes rather than generating an unbounded burst of provider queries.
- The managed control-plane limitations documented for `v0.1.168-ts.1`, including the residual Bundle Installer recovery path and lack of automatic old-image retention, are unchanged. This release deliberately does not mix deployer or activator changes with payment behavior.
