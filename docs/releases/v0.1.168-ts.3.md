# TokenSupply v0.1.168-ts.3

## Highlights

- Replaces the fragile shell control-plane activator with a stable, testable Go entry point so managed Docker updates can recover from interrupted deployer self-upgrades.
- Adds strict staged-payload verification, atomic deployer replacement and rollback, bounded timer recovery, and audited root-only recovery commands.
- Adds a real Ubuntu systemd release gate that exercises consecutive control-plane upgrades, idempotent replay, crash recovery, malformed requests, and failed-target rollback before a release tag can be created.

## Fork Changes

- Moves host activation to the long-lived `sub2api-deployer --activate-staged-control-plane` contract. The normal once-per-minute timer invocation exits cleanly and silently when no request exists, even while the deployer daemon is running.
- Limits runtime self-upgrade to the root-owned `/usr/local/sbin/sub2api-deployer` executable. systemd units, timers, tmpfiles, and sandbox policy remain Bundle Installer assets and cannot be selected by an image manifest.
- Verifies request, status, state, candidate container identity, immutable image digest, runtime manifest, architecture, ownership, mode, and SHA-256 before replacement. Symlinks, unexpected paths, stale job identity, unsafe systemd paths, and unit drop-ins fail closed.
- Replaces the deployer atomically, checks its build identity and Unix-socket health, and restores the previous bytes if restart or health verification fails. Replaying the same SHA is a no-op and does not restart the service.
- Uses one activation lock for manager staging, request publication, timer activation, and operator recovery. The request is published only after its supporting state is durable and the application deployment has reached its successful terminal state.
- Adds bounded retry and boot recovery. Malformed requests are quarantined with a terminal status; pending state older than ten minutes is surfaced as failed or unknown instead of remaining indefinitely in an updating state.
- Adds root-only `control-plane status`, `control-plane retry`, and `control-plane quarantine` commands with job-identity, application-health, no-running-job, reason, and audit checks.
- Requires the effective activator unit to have exactly the expected `ExecStart`, no drop-ins, and an enabled and active timer. An incompatible host is rejected before application traffic switches and is directed to the Bundle Installer.
- Makes the Installer transactionally switch from the legacy shell activator to the stable Go entry point, verify the effective unit and no-request behavior, and remove the retired shell only after validation. Failure restores the old deployer, unit, timer, shell, and service state without restarting the application container.
- Removes the obsolete bootstrap curl that omitted the immutable target digest and updates the permanent managed-update and Bundle documentation.
- Binds Build Once candidates to the exact workflow commit and Git blob identities used by Preflight, Promote, and Release. Candidate evidence and control-plane manifests are retained as permanent Release assets.
- Keeps the public completion ledger at schema 3 for this bridge release so a `v0.1.168-ts.2` application can authenticate and start the update. Workflow identity is still enforced before tag creation and publication; schema 4 remains a later compatibility step.

## Upstream Changes

## Configuration And Migrations

- No database migration, schema change, application setting, or environment variable is included.
- `v0.1.168-ts.2` and `v0.1.168-ts.3` application containers remain database-compatible during blue-green deployment.
- The host control-plane layout changes once: an existing `v0.1.168-ts.2` installation must run the `v0.1.168-ts.3` Bundle Installer before starting the application update from the administrator page.

## Deployment And Rollback

- Download the Bundle for the host architecture from this completed Release, verify `MANIFEST.sha256`, back up `/var/lib/sub2api-deployer` and the installed host assets, and run the Bundle Installer once. This migrates only the host control plane; it must not restart or replace the currently serving application container.
- Verify that `sub2api-deployer-upgrade.service` effectively runs `/usr/local/sbin/sub2api-deployer --activate-staged-control-plane`, has no drop-ins, the upgrade timer is enabled and active, the retired `/usr/local/sbin/sub2api-deployer-upgrade` shell is absent, and a no-request service invocation exits successfully without restarting the deployer.
- After that host migration succeeds, start the `v0.1.168-ts.3` application update from the administrator page. Verify the immutable target digest, candidate health, traffic switch, drain, active version and container ID, `degraded=false`, and control-plane activation terminal status.
- If the Installer fails, it restores the previous host assets while the current application continues serving. If runtime activation fails, the activator restores the previous deployer and preserves explicit recovery evidence for the root-only commands or Bundle Installer procedure.
- Because this release has no migration or incompatible persisted format, the application can roll back to `v0.1.168-ts.2`. Do not delete or overwrite a published tag, image, candidate, or completion ledger.

## Known Limitations

- `v0.1.168-ts.2` cannot repair its legacy activator through the web path. The one-time `v0.1.168-ts.3` Bundle Installer migration is mandatory before clicking update; skipping it must fail closed before traffic switches.
- A defect in the currently running deployer's image extraction or staging path, or a change to systemd units, timers, tmpfiles, or sandbox policy, still requires the Bundle Installer. Keeping that bootstrap boundary small and explicit is safer than duplicating Docker and trust logic in the activator.
- Automatic retention of old Docker images is not included. Operators must monitor disk usage and apply a separately reviewed retention policy; retained rollback images must not be removed blindly.
- If an untagged Build Once candidate digest is deleted externally before promotion, publication fails safely and the candidate must be rebuilt from a new audited commit. The workflow does not recreate or silently substitute missing immutable content.
- The public completion ledger remains schema 3 only for `v0.1.168-ts.2` compatibility. A later release may move workflow identity into schema 4 after `v0.1.168-ts.3` is the minimum supported managed-update baseline.
