# TokenSupply v0.1.168-ts.4

## Highlights

- Adds an opt-in A5 compatibility mode to EasyPay so the new platform can use its own payment, active order-query, and full-refund behavior without changing standard EasyPay.
- Sends A5 a clean browser return URL, avoiding the malformed query string produced when A5 HTML-encodes embedded separators.
- Makes uncertain refunds recoverable: local deduction rollback, the pending order state, and required audit evidence are committed together, then an administrator can query the platform and finalize the result safely.

## Fork Changes

- Adds a `standard` / `a5` compatibility selector to each EasyPay provider instance. `standard` remains the default and retains the existing concrete provider and request/response behavior.
- Implements A5 active payment queries and full refunds with strict merchant, order, amount, status, and response validation. Unknown network or platform outcomes enter a queryable pending state instead of being reported as a definite failure.
- Keeps new EasyPay orders bound to the compatibility mode recorded in their schema-v3 provider snapshot. A missing or unknown schema-v3 mode fails closed.
- Supports querying `v0.1.168-ts.3` pending-refund audit records while rejecting incomplete or inconsistent state for manual reconciliation.
- Commits deduction rollback, `REFUND_PENDING`, and its required audit record in one transaction. Final queried deductions, the terminal order state, and `REFUND_SUCCESS` are also one transaction.
- Restores refunded balance through the neutral balance-adjustment path so rollback does not inflate cumulative recharge statistics.
- Keeps standard EasyPay empty-transaction-number refunds on their previous behavior and prevents A5 compatibility logic from leaking into standard mode.

## Upstream Changes

- Baseline remains upstream `v0.1.168` at `5a6143097db142b72a6fc848c214e97214470bdd`; this release does not synchronize additional upstream commits.

## Configuration And Migrations

- Database migrations: None.
- New setting: EasyPay provider instances have an optional `compatibilityMode`. The default is `standard`; select `a5` only for an A5 instance.
- A5 must use a newly created, separate provider instance. Do not repurpose an instance that has historical standard EasyPay orders, because schema-v2 orders created before this release do not record their original dialect.
- A read-only production preflight on 2026-07-31 confirmed the current standard history and A5 traffic use distinct provider instances and merchant identities with non-overlapping creation windows. Sensitive identifiers are intentionally omitted.
- `v0.1.168-ts.3` and `v0.1.168-ts.4` remain database-compatible. Do not enable the A5 mode until the `v0.1.168-ts.4` deployment is active; the older application does not understand the new protocol selection.

## Deployment And Rollback

- The existing `v0.1.168-ts.3` managed deployer can install this release through the administrator update flow after the Release workflow and completion ledger are successful. No Bundle Installer or host control-plane migration is required.
- Before updating, back up the database and deployer state. Confirm the current A5 provider is a separate instance, then leave its compatibility mode unchanged until the new application is active.
- After traffic switches, set that separate instance to `a5`. Verify application health, payment creation and browser return, callback crediting, active order query, a controlled full refund, pending reconciliation, active image digest, and `degraded=false`.
- No schema migration or incompatible persisted format blocks rollback to `v0.1.168-ts.3`. Before rolling back, disable the A5 instance so the older application cannot accept or refund A5 orders using standard EasyPay semantics; re-enable it only after `v0.1.168-ts.4` is restored.
- Do not delete or overwrite a published tag, image, candidate, checksum, or completion ledger.

## Known Limitations

- A5 compatibility supports full refunds only. Partial refunds are rejected before a platform request is sent.
- Schema-v2 EasyPay orders do not contain a compatibility mode. The release therefore requires a separate A5 provider instance and must not be used to convert an instance with standard EasyPay history.
- Concurrent queries of the same still-pending refund can create duplicate informational audit rows because the idempotent audit helper has no database uniqueness constraint. This does not change funds, deductions, or order state.
- A5 is an external platform. Unavailable or inconclusive responses remain pending and may require later query or manual reconciliation rather than being guessed as success or failure.
