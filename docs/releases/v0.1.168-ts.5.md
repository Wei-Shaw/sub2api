# TokenSupply v0.1.168-ts.5

## Highlights

- Adds per-channel controls for OpenAI Standard, Priority, and Flex service tiers, including an enable switch and a configurable billing multiplier for each tier.
- Applies the selected channel policy consistently to HTTP, WebSocket, Images, Messages/Chat compatibility, Grok bridge, embeddings, Alpha Search, and cyber-policy billing paths.
- Bills from the upstream tier actually delivered when that information is available, while preserving the request and channel-policy snapshots needed for consistent settlement.

## Fork Changes

- Adds the service-tier controls to the administrator channel editor. Defaults are Standard `1.0x`, Priority `2.0x`, and Flex `0.5x`; multipliers must be between `0.01x` and `100x`, and at least one tier must remain enabled.
- Normalizes OpenAI protocol aliases for policy and billing: `fast` uses Priority, `scale` uses Standard, and `auto` / `default` use Standard. Native Grok continues to reject unsupported non-standard tiers before an upstream request.
- Captures a per-request or per-WebSocket-turn channel policy so a request is checked and billed against one coherent configuration. Expired active-channel cache entries fail closed instead of serving an indefinitely stale policy.
- Uses the upstream-reported actual tier for final billing where supported, including fallback and special settlement paths, and emits structured mismatch logs when the delivered tier differs from the outbound tier.
- Adds optimistic concurrency protection to the current administrator UI. A stale channel edit receives `409 CHANNEL_UPDATE_CONFLICT` instead of silently overwriting a newer edit.
- Prevents tier multipliers from being applied twice by replacing the previous global LiteLLM tier surcharge with the channel policy as the single service-tier multiplier source.

## Upstream Changes

- Baseline remains upstream `v0.1.168` at `5a6143097db142b72a6fc848c214e97214470bdd`; this release does not synchronize additional upstream commits.

## Configuration And Migrations

- Migration `200_add_channel_service_tier_config.sql` adds the nullable JSONB column `channels.service_tier_config` without a database default, plus a `NOT VALID` object-shape constraint for non-null writes. This expand-only form avoids a table rewrite or validation scan during deployment.
- New environment variables: None.
- The new application interprets a legacy `NULL` as the versioned Standard `1.0x`, Priority `2.0x`, and Flex `0.5x` policy, then writes the complete object when a channel is created or updated. Old application binaries ignore and preserve the additive column, so old/new containers can coexist during a managed blue-green deployment.
- Invalid persisted policies and unknown active-channel policy snapshots fail closed after the bounded 15-minute cache window.

## Deployment And Rollback

- Deploy through the managed administrator update flow only after the Release workflow and completion ledger are successful. No Bundle Installer or host control-plane migration is required.
- Before updating, back up the database and deployer state. After traffic switches, verify migration 200, channel settings save/reload, one controlled Standard/Priority/Flex request, the resulting usage multiplier, active image digest, application health, and `degraded=false`.
- Migration 200 is additive and does not block an image rollback to `v0.1.168-ts.4`. The column and configured values remain in the database for a later re-upgrade.
- `v0.1.168-ts.4` does not enforce these new tier switches or multipliers. If a custom restriction is required for safety or cost control, disable the affected channel before rollback or explicitly accept the older behavior until `v0.1.168-ts.5` is restored.
- Do not delete or overwrite a published tag, image, candidate, checksum, or completion ledger.

## Known Limitations

- An abnormal or malicious multipart Images request can contain duplicate `service_tier` fields. When policy evaluation leaves the selected tier unchanged, the forwarded multipart body can retain those duplicates; an upstream that interprets the first value instead of the last could execute a different tier. Normal SDK requests contain one field. A follow-up should always canonicalize or reject duplicate tier fields.
- Very old cached administrator pages may omit `expected_updated_at`. They remain compatible but cannot detect another administrator update that completed before the legacy request reached the service. The current UI always sends the revision and rejects stale writes.
- Requested-versus-actual tier mismatches are written to structured logs but are not yet persisted as a long-term operations metric.
- `/v1/live` and batch image request schemas do not expose `service_tier`; those protocols therefore do not offer these per-request tier choices.
