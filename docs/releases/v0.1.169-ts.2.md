# TokenSupply v0.1.169-ts.2

## Highlights

- Fixes Fast/Priority billing for OpenAI-compatible upstreams that accept `priority` but return `default` or omit a trustworthy service tier.
- Adds one channel-level billing-authority switch beside the existing Standard, Fast/Priority, and Flex multipliers. The setting applies uniformly to OAuth and API Key accounts.

## Fork Changes

- When **Bill by the tier sent upstream** is enabled, the tier actually sent upstream is authoritative for OAuth and API Key billing. A Fast request sent as `priority` therefore keeps the configured Priority multiplier even when the response reports `default`.
- When the switch is disabled, a recognized response tier is authoritative for both account types. Missing or unknown response tiers still fall back to the outbound tier because no reliable response tier is available.
- Response tiers remain available as diagnostic observations while outbound billing is authoritative, without creating false `service_tier_mismatch` or service-quality degradation warnings.
- The request-level channel snapshot continues to apply the selected service-tier multiplier exactly once across normal HTTP, Images, Embeddings, Chat/Responses, Messages, Grok, WebSocket/WebSocket v2, and cyber-policy usage paths.
- Channel audit logs now record the billing-authority switch before and after administrator updates.

## Upstream Changes

- Baseline remains upstream `v0.1.169` at `682c4fe0e61b851508fa976ac693e0f68a0639eb`.
- No additional upstream commits are included after `v0.1.169-ts.1`; this is a TokenSupply billing hotfix release.

## Configuration And Migrations

- No database migration or environment variable is added.
- `channels.service_tier_config` gains the additive `use_outbound_tier_for_billing` JSON field.
- The setting defaults to enabled for new channels, existing database JSON, and old browser clients that omit the new field. An explicit `false` remains preserved.
- The setting is enabled by default because OAuth and compatible API Key upstreams may normalize accepted Fast requests to `default` in their responses. Administrators should disable it on a channel if that upstream's response tier, rather than the requested tier, is the billing authority.
- Blue-green coexistence is supported: older application versions ignore the extra JSON field, while the new version safely interprets legacy JSON.

## Deployment And Rollback

- Publish and deploy only through the managed Release workflow and deployer. Do not create or replace a tag locally.
- Before deployment, verify the completion ledger, OCI digest, active version, active container, public health, and `degraded=false`.
- After switching traffic, send one controlled Fast request through an affected channel. Confirm the outbound tier is `priority`, the usage record is `priority`, the configured multiplier is applied once, and no false mismatch warning is emitted.
- Keep `v0.1.169-ts.1` and its inactive slot available until health and billing observations remain stable for at least five minutes.
- No migration or irreversible data change prevents image rollback. Rolling back to `v0.1.169-ts.1` restores its previous OAuth/API Key billing-authority behavior.

## Known Limitations

- With outbound-authoritative billing enabled, an upstream that silently ignores `priority` can still be charged using the configured Priority multiplier. This is the explicit policy selected by the channel setting; disable it when the upstream response is the authoritative source.
- When response-authoritative billing is selected but the response omits or reports an unknown tier, billing falls back to the outbound tier rather than inventing a Standard result.
- The existing managed-deployer limitations, including the need for a Bundle Installer when a host's control-plane extraction path itself is broken and the lack of automatic old-image retention, remain unchanged.
- CI cannot prove a third-party upstream actually honors Fast. A controlled production Fast request and billing observation remain required after deployment.
