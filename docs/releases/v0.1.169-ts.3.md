# TokenSupply v0.1.169-ts.3

## Highlights

- Adds an image playground inside the authenticated dashboard for text-to-image, image-to-image, and combined reference-image plus prompt generation.
- Keeps long-running image generation behind asynchronous tasks, avoiding a single browser request that can exceed Cloudflare's request timeout.
- Gives users downloadable results, visible retention time, per-image expiry countdowns, and confirmed permanent deletion.

## Fork Changes

- Adds a feature-flagged dashboard entry where users can select an eligible image-only group, choose a model and supported generation options, upload up to the model's reference-image limit, and continue using the dashboard while generation runs in the background.
- Selects only a usable API key owned by the authenticated user in the chosen image-only group. Missing dedicated groups and missing group-specific keys produce actionable dashboard states.
- Reuses the existing OpenAI-compatible image gateway and usage pipeline, so administrator and user usage records retain user, API key, group, account, model, endpoint, token, image count, and cost identity.
- Separates text input, image input, text output, and image output tokens when model or channel pricing supplies distinct image rates, while retaining the established fallback behavior for legacy pricing.
- Stores generated results through the existing S3-compatible object-storage abstraction. Reference uploads remain temporary request data and are not retained by the playground.
- Adds persisted Redis cleanup jobs and a non-secret storage-target identity. Expired objects are retried by the cleanup worker, while changing the bucket or endpoint blocks deletion from a different target.
- Adds administrator controls for the dashboard feature flag and generated-file retention. Users see the active retention period and a live countdown on result cards and image details.
- Changes the former local-history clear action into a confirmed permanent delete that removes both the retained object and its task record; processing tasks are not deleted.

## Upstream Changes

- Baseline remains upstream `v0.1.169` at `682c4fe0e61b851508fa976ac693e0f68a0639eb`.
- No additional upstream commits are included after `v0.1.169-ts.2`; this release contains the TokenSupply image playground and its storage, accounting, and administration support.

## Configuration And Migrations

- No database migration is added.
- A new `image_playground_enabled` system feature flag controls the dashboard route and sidebar entry. It is disabled by default until an administrator enables it.
- Asynchronous image tasks require configured S3-compatible image object storage. Administrators may reuse the backup S3 connection while choosing a separate bucket or key prefix.
- Generated files default to a 24-hour retention period. Administrators can configure 1 through 168 hours; the user-facing playground reports the active value.
- Presigned download expiry is kept at least as long as retention, up to the S3 seven-day limit. A public base URL may be used instead of presigned result URLs.
- Settings and task fields are additive. Older application versions ignore the new feature flag and object-storage settings, while the new version continues to read legacy image-task records.

## Deployment And Rollback

- Publish and deploy only through the managed Release workflow and deployer. Do not create or replace a tag locally.
- Before enabling the playground, configure and test the S3-compatible target, confirm its write/read/delete permissions, and create at least one dedicated image group with a usable user-owned key.
- After deployment, generate one text-only image and one reference-image edit. Verify task completion, result download, user/admin usage records, separate image token costs, manual deletion, and object removal.
- Keep `v0.1.169-ts.2` and its inactive slot available until generation, download, usage accounting, and cleanup observations remain stable for at least five minutes.
- No migration or irreversible data change prevents image rollback. Rolling back to `v0.1.169-ts.2` removes the new dashboard route and worker behavior; existing Redis TTLs and stored objects should be retained until the new version is restored or an administrator performs controlled storage cleanup.

## Known Limitations

- Generated-image persistence depends on the configured third-party object store. The application cannot validate provider permissions beyond the administrator connection test and real upload/download/delete operations.
- Expiry is a deadline, not a hard real-time deletion guarantee. The cleanup worker scans every five minutes, so physical object deletion can occur several minutes after the countdown reaches zero and can be delayed further by a temporary object-store outage.
- All images produced by one generation task share one retention deadline. The detail view shows that shared countdown for the currently selected image.
- Changing the object-storage bucket or endpoint intentionally stops cleanup of objects associated with the previous target. Restore the previous target before deleting those retained files; the service will not guess or delete from the new target.
- Reference images are sent to the selected upstream for generation but are not stored by the playground. Their retention and training treatment after submission depend on that upstream's policy.
- The existing managed-deployer limitations, including the need for a Bundle Installer when a host's control-plane extraction path itself is broken and the lack of automatic old-image retention, remain unchanged.
