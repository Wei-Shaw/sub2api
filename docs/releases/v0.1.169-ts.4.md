# TokenSupply v0.1.169-ts.4

## Highlights

- Fixes GPT Image multi-image generation for OAuth-backed channels without sending the unsupported `tools[0].n` parameter.
- Makes retained Image Playground history available across browsers for the same account while preventing one account from listing, previewing, downloading, or deleting another account's tasks.
- Keeps generated image objects private: neither dashboard nor asynchronous API responses expose object-store URLs, presigned URLs, or image bytes stored in Redis.
- Adds a compact collapse control for the Image Playground generator.

## Fork Changes

- Fans out non-streaming OAuth image requests with `n > 1` into ordered single-image requests and merges the generated images into one response.
- Aggregates real token usage across all successful upstream image requests, preserves usage from partial failures for billing, and uses the final upstream response for quota-header snapshots.
- Rejects unsupported streaming OAuth multi-image requests explicitly instead of forwarding an invalid tool parameter.
- Adds a server-owned per-user Redis history index for the 24 most recent retained Image Playground tasks. The first history request lazily backfills still-valid tasks created before this index existed.
- Uses the authenticated dashboard identity for list, detail, preview, download, and delete operations. Foreign or guessed task IDs return not found, and malformed or foreign Redis index entries are filtered and pruned.
- Stores only private object keys for generated images. Upstream `url`, `image_url`, `download_url`, and `b64_json` fields are recursively removed before Redis persistence and sanitized again when legacy records are returned.
- Serves dashboard image bytes only through JWT-authenticated owner-scoped endpoints. Asynchronous API image bytes require the same user and exact API key that created the task; another key owned by the same user receives not found.
- Stops returning object-storage URLs to the dashboard. Protected previews are fetched through the authenticated API as browser-local Blob URLs and released when tasks are deleted or the page closes.
- Loads only the first image needed by each gallery card, then fetches the remaining images when the user opens task details.
- Adds a desktop and mobile composer toggle. Desktop starts expanded, while smaller screens remain compact by default.
- Leaves synchronous `/v1/images/generations` and `/v1/images/edits` response behavior unchanged.

## Upstream Changes

- Baseline remains upstream `v0.1.169` at `682c4fe0e61b851508fa976ac693e0f68a0639eb`.
- No additional upstream commits are included after `v0.1.169-ts.3`; this release contains TokenSupply image-generation compatibility, history, authorization, and interface fixes.

## Configuration And Migrations

- No database migration or new application setting is added.
- Redis per-user history keys are additive, created lazily, and expire automatically. Existing unexpired image tasks remain readable and are indexed on first access.
- Existing image storage, retention, feature flag, group, model, and user API-key settings remain compatible.
- Legacy `public_base_url` and `presign_expiry_hours` fields may remain in an existing config file for parser compatibility, but this version ignores them and removes them from the administrator interface.

## Deployment And Rollback

- Publish and deploy only through the managed Release workflow and blue-green deployer. Do not create or replace a tag locally.
- Deploy the new application and confirm the new slot is healthy before making the image bucket private or disabling the legacy public object route. During blue-green coexistence, the old application still depends on the previous storage access policy.
- After the new application is active, make the MinIO bucket private, clear the legacy public base URL, and configure every external `/image-objects/*` request to return 404.
- Verify text-to-image and reference-image generation, a two-image OAuth request, usage totals, final quota headers, authenticated preview and download, permanent deletion, and a legacy public object URL returning 404.
- Verify history from a second browser signed into the same account. Then use a different account to confirm that list results are isolated and that guessed task detail, preview, download, and delete requests return not found.
- Keep `v0.1.169-ts.3` and its inactive slot available until generation, storage, billing, and cross-browser observations remain stable for at least five minutes.
- No schema or irreversible data change prevents rollback. Before routing traffic back to `v0.1.169-ts.3`, restore the previous MinIO read policy and Nginx object route; otherwise the old application cannot read retained results.

## Known Limitations

- OAuth multi-image generation uses sequential upstream requests. Generation time grows with the requested image count, although Image Playground jobs continue asynchronously beyond the browser and Cloudflare request window.
- The dashboard retains and lists at most the 24 most recent unexpired tasks. Full prompts and uploaded reference files are not synchronized across browsers; only the task's stored prompt preview and input-image count are available there.
- Protected dashboard previews proxy image bytes through the application and use a 60-second fetch timeout. A temporary object-store or network failure can leave a completed card waiting for its preview until the page is refreshed.
- Legacy completed tasks that contain private storage keys remain readable. A legacy task containing only a public result URL is deliberately sanitized and cannot be downloaded through the new authenticated endpoints.
- Generated-image persistence still depends on the configured object store. The service fails closed when the storage target identity changes and will not read or delete from a different bucket by guesswork.
- The existing managed-deployer limitations, including the lack of automatic old-image retention, remain unchanged.
