# TokenSupply v0.1.169-ts.6

## Highlights

- Prevents a safe pre-switch deployment rejection from being reported as an automatic rollback failure or as an application update that already took effect.
- Checks the managed Nginx route and the currently routed application before creating an update task or changing any container.
- Keeps confirmed pre-switch failures retryable while reserving the red emergency state for real degraded, rollback-failed, or post-activation deployer failures.
- Updates the host deployer automatically through the existing verified control-plane upgrade path; no manual binary or container replacement is required.

## Fork Changes

- Adds a synchronous read-only deployment preflight that requires exactly one literal primary `proxy_pass` to `sub2api_managed` and confirms the old routed slot is healthy before a durable job is created.
- Retains the asynchronous route check immediately before candidate preparation so external Nginx changes after the synchronous check are still rejected.
- Distinguishes a failure before any traffic switch from an actual rollback: the former confirms old routed health without repeating the same failed route guard, while any attempted switch still requires strict route and health restoration checks.
- Stops failed pre-switch and rollback jobs from inheriting an unrelated control-plane upgrade status from a previous deployment.
- Shows a confirmed pre-switch update rejection as an amber “update not applied” warning with a retry action and hides unrelated historical rollback or control-plane details.
- Documents and tests the Nginx contract: the primary application location uses the single literal managed upstream, while approved health or CMS auxiliary locations use a variable proxy target.

## Upstream Changes

- Baseline remains upstream `v0.1.169` at `682c4fe0e61b851508fa976ac693e0f68a0639eb`.
- No additional upstream commits are included after `v0.1.169-ts.5`; this release contains the TokenSupply managed-deployment recovery hotfix.

## Configuration And Migrations

- No database migration, new environment variable, or new application setting is added.
- Existing blue/green state, Compose, Redis, PostgreSQL, object-storage, and application configuration remain compatible.
- The effective Nginx configuration must contain exactly one literal primary `proxy_pass http://sub2api_managed;`. Approved health and CMS fallback locations that follow the managed upstream must use a variable `proxy_pass`.
- The production site already follows this route contract before the release; no release-time manual Nginx edit is required.

## Deployment And Rollback

- Publish and deploy only through the managed Release workflow and managed deployer/UI. Do not manually create a tag, replace a container, copy a deployer binary, or edit deployer state.
- Before deployment, verify read-only that production has one literal primary managed route, the active slot is healthy, no deployment job is running, and `degraded=false`.
- The current `v0.1.169-ts.5` deployer performs the blue/green application update, verifies the bundled control-plane manifest and checksums, and atomically activates the `v0.1.169-ts.6` deployer after the application is stable.
- Verify application version and digest, active slot and port, public health, deployer version and commit identity, control-plane status, 5xx responses, and container restarts for at least five minutes.
- Keep `v0.1.169-ts.5` in the inactive slot. Rollback is schema-safe because this release has no migration or shared-data format change.

## Known Limitations

- The `v0.1.169-ts.5` deployer executes this one application update before the new preflight implementation is activated. Production must therefore satisfy the documented route contract before starting the update.
- Variable-based auxiliary routing is an operator configuration contract rather than a full Nginx syntax parser rule. The deployer continues to strictly count the one literal primary route and verify the routed slot and upstream port.
