# TokenSupply v0.1.170-ts.1

## Highlights

- Synchronizes the fork with upstream `v0.1.170`, including opt-in group profit control and broader upstream billing-rate probing and writeback.
- Makes the operations dashboard easier to read with RPM, K token/s, actual deductions, sortable TTFT details, p95/p99/max TTFT alerts, and real traffic charts.
- Consolidates email-policy saving, refreshes TokenSupply email and announcement presentation, and adds an administrator switch for customer-service visibility.
- Adds the total balance across non-deleted users and updates the Codex setup snippets to the current TokenSupply model defaults.

## Fork Changes

- Uses blue for healthy channel and first-token indicators, excludes disabled background jobs from health-score deductions, and shows the backend-provided deduction reasons.
- Reworks operations throughput displays around RPM, K token/s, and actual user deductions. Request details include TTFT and total duration, and TTFT can be sorted by length.
- Adds TTFT p95, p99, and maximum alert metrics. The evaluator uses a dedicated, bounded TTFT query and reuses matching results within one evaluation pass instead of loading the complete dashboard for every rule.
- Adds a larger switchable real-traffic chart and prevents stale requests from replacing data for a newer filter or after realtime monitoring is disabled.
- Moves email channel-policy saving into the main settings save action, blocks duplicate concurrent submissions, and reports partial success accurately when the policy saves but ordinary settings do not.
- Refreshes the default email templates and announcement center with TokenSupply's neutral black, white, gray, and blue design language while preserving the existing TS mark and HTML escaping.
- Adds the persisted `customer_service_enabled` setting and places the customer-service entry beside the model plaza when enabled.
- Shows administrators the database-calculated total balance across all non-deleted users.
- Updates all four existing Codex configuration combinations to use `gpt-5.6-sol`, `codex-auto-review`, and high reasoning without removing any setup variant.

## Upstream Changes

- Baseline moves from upstream `v0.1.169` at `682c4fe0e61b851508fa976ac693e0f68a0639eb` to upstream `v0.1.170` at `7e2e9ba05026b7126318aa0754c1afa0ac00bc58`.
- Upstream billing probes now support eligible API-key accounts across the supported platforms, avoid known official-provider domains, and use longer backoff for unsupported targets.
- Accounts can optionally synchronize a validated upstream-declared base rate into their account multiplier. Compare-and-swap protection prevents a stale probe from overwriting a concurrent administrator edit, and synchronized changes are logged.
- Groups can opt into profit control for token traffic. The scheduler filters accounts whose cost exceeds the configured downstream margin threshold while preserving normal ordering, stickiness, failover limits, and request-time pricing consistency.
- Profit-control details remain administrator-only, dedicated media and non-token paths keep their established billing behavior, and the included preview command can evaluate a proposed policy before enabling it.

## Configuration And Migrations

- Adds migrations `201_group_profit_control.sql` and `202_group_profit_control_auth_cache_invalidation.sql`. They append nullable profit-control columns and update auth-cache invalidation without rewriting previously released fork migrations.
- The new columns have no database defaults, so `v0.1.169-ts.6` and `v0.1.170-ts.1` containers can coexist during blue-green deployment. Legacy NULL values are interpreted as disabled or zero by the new application.
- Adds per-group profit-control settings, per-account upstream billing probe and rate-sync settings, and the global `customer_service_enabled` setting. Existing customer-service visibility remains enabled by default for backward compatibility.
- No new environment variable is required.

## Deployment And Rollback

- Publish only through the managed Release workflow, then deploy from the administrator update page after the immutable image and completion ledger are available. This release does not change the deployer or control-plane activation protocol.
- During deployment, verify migrations `201/202`, application version and digest, active slot and port, public health, `degraded=false`, background-job health, and the operations dashboard queries before declaring the update complete.
- Rollback to `v0.1.169-ts.6` remains application-compatible. The old application ignores the added nullable columns; the trigger replacement is reviewed as backward-compatible and remains in the database after image rollback.
- Persisted administrator changes made through new settings are valid shared data. Disable profit control or rate synchronization before rollback when the intended behavior must stop immediately.

## Known Limitations

- Email channel policy and ordinary SMTP settings remain two backend API calls and cannot commit as one database transaction. The UI prevents duplicate submission and clearly reports partial success so an administrator can retry safely.
- TTFT alert queries use the existing two-second latency-query timeout. On a very large unindexed usage table, evaluation safely reports a query failure instead of producing a false alert.
- Total user balance is one administrator-only aggregate query. It is not an N+1 query, but extremely large user tables may increase the user-list response time.
- Existing managed-deployment limitations, including operator recovery for bootstrap-layer failures and the deferred old-image retention policy, are unchanged.
