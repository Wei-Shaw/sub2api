# TokenSupply v0.1.170-ts.2

## Highlights

- Recovers provider-verified payments even when the local order expired or was cancelled before fulfillment, while keeping refunded orders terminal and fulfillment idempotent.
- Adds an administrator error-log explorer backed by the same records as the operations error summary, and reuses the full usage-record table for TTFT request details.
- Corrects TTFT percentile sample and alert semantics, shows insufficient-sample states, and makes firing and recovery email delivery durable and retryable per recipient.
- Makes Passkey/WebAuthn configuration available to Docker Compose and the managed deployer in this release.

## Fork Changes

- Removes the fixed late-payment recovery window. A payment confirmed by the provider can complete after local expiry or cancellation; concurrent expiry and fulfillment remain serialized by the existing database transaction and row lock.
- Preserves `REFUNDED` as a terminal payment state and does not reopen or credit refunded orders.
- Adds a paginated operations error-log explorer with the same administrator authorization, error scope, and data contracts used by the dashboard summary.
- Replaces the compact TTFT detail view with the shared administrator usage table. The view supports platform, TTFT-presence, exact time-window, TTFT, and duration filtering or sorting.
- Resolves composite-group platform filters through a single groups/accounts join instead of correlated per-row subqueries.
- Advances the operations alert evaluator to v3. Percentile alerts distinguish insufficient samples from healthy results, use corrected P95/P99/maximum sample semantics, sustain firing and recovery state, and preserve Shadow mode and cooldown behavior.
- Retries a missed firing notification before processing recovery or unavailable metrics. Delivery is tracked per recipient, duplicate durable deliveries repair legacy event markers, and partial recipient failures remain retryable.
- Passes optional `WEBAUTHN_ENABLED`, `WEBAUTHN_RP_DISPLAY_NAME`, `WEBAUTHN_RP_ID`, and `WEBAUTHN_RP_ORIGINS` through standard Docker and managed-deployer Compose assets. Unset variables do not override an existing `config.yaml`.

## Upstream Changes

- Baseline remains upstream `v0.1.170` at `7e2e9ba05026b7126318aa0754c1afa0ac00bc58`; this fork revision contains no additional upstream synchronization.

## Configuration And Migrations

- Adds migrations `203_normalize_ttft_alert_minimum_bad_count.sql`, `204_expand_ops_alert_evaluation_status.sql`, `205_validate_ops_alert_evaluation_status.sql`, and `206_drop_ops_alert_evaluation_status_v2.sql`.
- Migration `203` normalizes percentile-alert `minimum_bad_count` values to zero. Migrations `204-206` add the v3 status constraint as `NOT VALID`, validate historical rows separately, and then remove the old v2 constraint so the stronger table lock is not retained during the scan.
- The v3 status set is a strict superset of v2, so `v0.1.170-ts.1` and `v0.1.170-ts.2` application containers can coexist during a managed blue-green update.
- Passkey remains disabled unless explicitly configured. Production activation requires HTTPS, a domain-only RP ID, and one or more comma-separated exact browser origins. Example values are documented in `deploy/.env.example`.
- No payment-provider configuration change is required.

## Deployment And Rollback

- Publish only through the managed Promote Release workflow after this Release PR and its merged `main` SHA pass all required gates. Deploy production separately from the administrator update page after the immutable image, digest, checksums, and completion ledger are available.
- Before enabling Passkey, place all four `WEBAUTHN_*` values in the managed environment, verify the public HTTPS origin, and test both registration and login. Leaving the variables unset preserves current behavior.
- During rollout, monitor migration lock failures, public health and active-slot handoff, payment fulfillment conflicts, operations endpoint latency, alert status distribution, notification queue errors, and duplicate email indicators.
- Image rollback to `v0.1.170-ts.1` remains application-compatible. Migrations `203-206` remain in the database after rollback; their accepted values are compatible with the old writer. Already recovered paid orders remain paid.
- Disable or unset Passkey configuration before rollback when authentication through the previous image has not been verified.

## Known Limitations

- Payment recovery still depends on the provider callback, return flow, or active-query path obtaining a verified provider result. This release does not repair an unavailable or incorrect provider response.
- The administrator TTFT detail view can request an exact count across a 30-day filtered window. The platform query no longer performs correlated per-row lookups, but very high usage volume can still increase query latency and must be monitored after deployment.
- Passkey credentials are bound to the configured RP ID and exact HTTPS origins. Incorrect values prevent registration or login; the application intentionally does not infer them from request headers.
- Image rollback does not reverse migrations or already committed payment and alert-delivery records.
