# TokenSupply v0.1.172-ts.1

## Highlights

- Updates the upstream baseline to `v0.1.172`, bringing OAuth account-takeover protection, safer OpenAI stream recovery, stricter request conversion, transport timeouts, billing precision fixes, and other gateway reliability improvements.
- Corrects operations error ownership and alert categories so provider failures, platform capacity or credential failures, compatibility problems, client rejections, and recovered attempts are reported separately.
- Records the upstream response model in usage logs and exposes model-mismatch auditing while preserving HTTP, streaming, WebSocket, and frontend reporting paths.

## Fork Changes

- Preserves upstream response-model tracking across fork conflict resolution and adds audit coverage for HTTP, streaming, WebSocket, usage persistence, and administrator usage views.
- Keeps successful failover and stream recovery attempts out of final-failure and SLA totals while retaining their credential, capacity, compatibility, security, or provider-health signal.
- Prevents local user quota and concurrency limits, local group model availability, and known request-semantic errors from being counted as provider SLA failures, including records carrying stale upstream-attempt metadata.
- Separates unknown upstream 4xx responses from confirmed invalid requests. Confirmed 400/422 request errors remain client request errors when preserved as 4xx and become platform compatibility errors only when exposed through a gateway 5xx.
- Adds credential alert counts that exclude recovered and non-SLA rows, and aligns administrator operations labels with the corrected responsibility and alert families.

## Upstream Changes

- Baseline: upstream `v0.1.171` (`f0e7a9c7a23a7d02fb159b62fa809621eb0475a6`) -> upstream `v0.1.172` (`155c49496026e86c17637614f5452cc7486db10c`).
- Blocks OAuth account takeover through pending account exchange and improves Tencent captcha expiry, region, and CSP handling.
- Recovers pre-output OpenAI capacity-shed stream errors through failover, preserves terminal stream behavior, and avoids cooling accounts for endpoint-specific or HTML count-token errors.
- Adds explicit upstream TCP dial timeouts, system-log sink backoff, midnight subscription quota reset, and fixed-scale usage billing quantization.
- Improves Responses tool-schema normalization, Responses-to-Anthropic content conversion, Codex WebSocket continuation, Grok failover, composite-group model display, Codex identity defaults, and EasyPay UTF-8 error handling.

## Configuration And Migrations

- No new fork-specific environment variable or administrator setting is required.
- Migration `207_add_usage_log_upstream_response_model.sql` adds nullable response-model audit fields. Migration `208_add_usage_log_upstream_model_mismatch_index_notx.sql` adds the matching non-transactional index. Older application images ignore the additive fields.
- Migration `209_reclassify_confirmed_upstream_failures.sql` installs the classification-v3 mixed-writer function and `BEFORE INSERT` trigger in a short transaction. It normalizes writes from a draining or rolled-back v2 image while v3 writers bypass it.
- Migration `210_backfill_ops_error_classification_v3.sql` runs 15 ordered historical `UPDATE` statements in a separate transaction. This keeps the trigger available before the longer backfill starts and allows old-version inserts to continue during the rewrite.
- Migrations `207` through `210` are marked and tested as compatible with image-only rollback. Reclassification changes metadata only; raw status codes and sanitized error messages remain unchanged.

## Deployment And Rollback

- Publish only through the controlled Promote Release workflow after this Release PR and the merged `main` SHA pass all required gates. Deploy production separately through the administrator update page after the immutable image, digest, checksums, and completion ledger are available.
- During deployment, observe application health, database migration completion, error rates, and the availability, provider-health, credential, capacity, compatibility, client-quality, and security alert families.
- Image rollback to `v0.1.171-ts.1` remains database-compatible. Application rollback does not restore an older PostgreSQL backup automatically because that could overwrite orders, users, and usage created after the update.

## Known Limitations

- Migration 210 intentionally performs selective evidence-based reclassification. Some much older classification-v0 local request records can remain unknown in long custom reporting windows rather than being guessed from incomplete data.
- A legacy 499 record that has lost all upstream phase, source, type, and prefix evidence can still theoretically resemble a client cancellation. Production-oriented fixtures cover preserved upstream evidence, but ambiguous evidence-free history is left unchanged.
- Historical backfill time, WAL volume, and table bloat scale with `ops_error_logs`; they were not benchmarked on the production database specification. The mixed-writer trigger and concurrent-insert behavior were verified with real PostgreSQL.
- External-provider behavior is covered by upstream and fork tests but was not replayed against every live provider during release preparation.
