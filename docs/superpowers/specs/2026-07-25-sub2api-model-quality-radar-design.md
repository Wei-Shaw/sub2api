# sub2api 模型质量雷达设计规格

- 状态：用户已确认，进入实施计划阶段
- 日期：2026-07-25
- 目标平台：`sub2api`
- 读者：管理层、技术负责人、架构师、质量团队、研发与 SRE

## 1. 执行摘要

本方案为 `sub2api` 建设内置的模型质量与路由健康雷达。雷达通过平台自建、受控的 Worker，持续运行版本化评测集，独立判定模型结果，并将能力、协议、路由、性能和成本证据关联到同一个评测样本。

雷达回答四个生产问题：

1. 某个模型或推理档位是否真的变差。
2. 下降来自上游模型、账号池/渠道、区域、路由策略还是协议转换。
3. 下降是否具有统计意义，是否达到告警或发布阻断标准。
4. 隔离渠道、回滚路由或恢复流量后，质量是否已经恢复。

方案采用“嵌入式质量控制面 + 独立 Worker/评分器”：

- 复用 `sub2api` 的模型目录、路由、账号池、权限、PostgreSQL、Redis 和 Vue 控制台。
- 新增评测计划、版本化题集、任务租约、路由证据、评分、基线、告警与发布门禁。
- 使用独立的 Python Worker、Docker/Kubernetes verifier 和可插拔开源评测适配器。
- 评测流量使用专用租户、API Key、预算和账号池，不占用客户流量配额。
- 第一阶段只告警不阻断，经过两周观察和阈值校准后启用强制门禁。

## 2. 背景与当前边界

### 2.1 sub2api 的实际定位

`sub2api` 是订阅额度分发型 AI API 网关，而不是训练平台或自有 GPU 推理集群。公开架构包含 Go 后端、Vue 控制台、PostgreSQL、Redis、上游账号池、协议适配、调度、限流、用量记录与计费。

本方案的核心风险链路是：

```text
客户端协议
  -> API Key 鉴权与租户限额
  -> 模型别名与路由规则
  -> 账号池/渠道调度
  -> 上游协议转换与调用
  -> SSE/非流式响应
  -> Token 统计、用量记录与结算
```

SFT/RLHF、训练任务、GPU 集群与千卡训练故障不在本期范围。它们可在未来作为新的评测执行域接入相同控制面。

### 2.2 Codex Radar 的可借鉴机制

Codex Radar/DRadar 采用分布式 Coding 任务矩阵：社区客户端运行模型并上传 Patch，服务端在干净环境独立执行 verifier，按任务通过率生成能力趋势。其公开客户端还包含租约、心跳、断点续跑、幂等补传、敏感信息扫描和独立判分。

本方案保留以下优点：

- 固定题集矩阵和版本化执行环境。
- 客户端执行与服务端判分分离。
- 结果必须通过独立 verifier，不相信执行端自报结论。
- 全量保留成本、耗时、步骤和任务历史。

本方案同时修正以下不足：

- 不以每题单次最新结果直接代表稳定能力，高波动任务重复运行。
- 使用成对基线比较、Bootstrap 置信区间和最小样本要求。
- 不把 Coding 通过率包装为通用 IQ；按能力域分别计分和门禁。
- 记录 `sub2api` 实际路由、账号池、渠道和重试证据，用于自动归因。
- 平台自建受控 Worker，减少志愿者机器、账号、网络和运行时间带来的混杂因素。

## 3. 目标、非目标与成功标准

### 3.1 目标

- 持续发现模型能力、协议正确性、服务性能、安全和成本退化。
- 区分上游模型退化与 `sub2api` 网关、路由、账号池或协议问题。
- 为版本发布提供可审计、可复现的质量准入证据。
- 为运营和 SRE 提供告警、诊断、隔离、复测和恢复闭环。
- 为企业客户提供透明但不泄露上游账号细节的模型健康视图。

### 3.2 非目标

- 第一阶段不采集客户原始 Prompt，也不从生产流量自动构造题集。
- 第一阶段不逐个账户执行完整 Benchmark，只在异常诊断时下钻账号池和渠道。
- 第一阶段不自动切换生产路由，只提供建议和受控人工操作。
- 不建设训练平台、标注平台或完整 Prompt 管理平台。
- 不保存或展示模型隐藏推理过程。

### 3.3 P1 成功标准

- 每个有效样本具备完整、可关联的路由和计费证据。
- Worker 崩溃、重复投递和上传重试不会重复计分。
- 注入已知模型、协议、路由和性能退化时，系统能正确发现并归因。
- 基础设施故障不会被误计为能力失败；异常分类准确率不低于 95%。
- 两周观察期内误报率低于 5%，用例不稳定率低于 2%。
- 评测并发、预算与上游调用受硬限制，不影响客户流量 SLO。
- 评测数据不包含客户 Prompt、上游凭据或隐藏推理过程。

## 4. 核心设计原则

1. **确定性与概率性分离**：协议、Tool Call、JSON、计费使用精确断言；开放回答使用统计和校准后的评分器。
2. **执行与判分分离**：Worker 负责调用和产出证据，独立评分器负责结论。
3. **基线不可漂移**：最新结果不会自动成为基线，基线必须显式审批和晋升。
4. **证据先于结论**：缺少路由证据、样本不足或置信区间过宽时显示“证据不足”，不宣称降级。
5. **能力与服务质量分离**：质量分、P99、错误率和成本分别告警，不能用更快掩盖更笨，也不能用更聪明掩盖不稳定。
6. **评测流量隔离**：使用独立租户、API Key、并发池、预算和可选专用账号池。
7. **可复现与可审计**：题集、Prompt、参数、镜像、评分器、路由规则和模型别名均需版本化。

## 5. 总体架构

```text
题集与基线库
  -> 评测编排器
  -> 平台受控 Worker 集群
  -> sub2api 专用评测入口
  -> 网关路由/账号池/上游模型
  -> 原始证据与网关 Route Trace
  -> 独立评分器
  -> 统计与异常检测
  -> 雷达看板、告警、发布门禁
```

### 5.1 组件职责

| 组件 | 主要责任 | 所属边界 |
| --- | --- | --- |
| 题集中心 | 用例、能力域、风险等级、环境与评分器版本 | Go 控制面 + 对象存储 |
| 评测编排器 | 生成矩阵、预算控制、定时/发布/事件触发 | Go 控制面 |
| 任务租约服务 | 原子领取、心跳、过期回收、幂等完成 | Go + PostgreSQL + Redis |
| 受控 Worker | 调用模型、执行 Coding 环境、上传证据 | Python + Docker/Kubernetes |
| 路由证据采集 | 实际模型、渠道、账号池、区域、重试、Token 与结算 | `sub2api` Go 网关 |
| 独立评分器 | 代码 verifier、精确断言、Judge 与安全评分 | Python 隔离服务 |
| 统计引擎 | 成对比较、置信区间、变化检测与切片 | Python 批处理/服务 |
| 基线与门禁 | 基线审批、规则版本、发布结论 | Go 控制面 |
| 雷达控制台 | 总览、模型矩阵、运行、告警、题集与规则 | Vue |

### 5.2 平台集成边界

雷达复用现有模型和路由配置，但不直接读取或展示上游账号凭据。网关在内部生成不可篡改的 `route_trace_id`，并将管理员可见的脱敏路由证据写入评测结果。

建议在既有 Admin API 下新增评测资源，而不是创建第二套身份系统。评测调用沿用公开模型协议，但必须携带平台签发、不可由普通客户伪造的评测上下文：

```text
evaluation_run_id
sample_id
dataset_version
expected_model_alias
expected_route_profile
```

这些字段由专用 API Key 与服务端上下文绑定。普通客户传入同名 Header 时应被忽略或拒绝，防止污染雷达数据。

## 6. 双轨评测体系

### 6.1 能力域

| 轨道 | 能力域 | 示例 | 主评分方式 |
| --- | --- | --- | --- |
| Coding/SWE | 代码修复 | 仓库 Issue、隐藏测试 | Docker verifier |
| Coding/SWE | 代码生成 | 函数实现、算法、编译 | 编译 + 单元/隐藏测试 |
| 通用 | 数学与推理 | GSM8K 类、逻辑题 | 标准答案/数值归一化 |
| 通用 | 指令遵循 | 格式、约束、多条件 | IFEval 类确定性规则 |
| 通用 | 长上下文 | 多位置事实召回 | 关键事实召回率 |
| 工具 | Tool Call | 工具选择与参数 | Schema + 执行结果 |
| 协议 | API 兼容 | OpenAI/Anthropic/Gemini、SSE | 精确事件与字段断言 |
| 安全 | 对齐与红队 | 越狱、注入、泄漏、过拒 | 分类器 + 盲评复核 |
| 服务 | 性能成本 | TTFT、P99、TPS、Token、扣费 | Trace 与压测数据 |

Coding 和通用能力分别计分。控制台可以展示一个总览状态，但任何发布门禁必须回到能力域和 P0 用例，不能只依据综合平均分。

### 6.2 题集结构

每条用例至少包含：

- 稳定 ID、能力域、重要等级和数据来源。
- Prompt/任务仓库版本、输入参数和预期模型能力。
- 执行镜像、资源上限、超时和网络策略。
- 评分器 ID、评分器版本、答案或 verifier。
- 是否允许重试、重复采样次数和成本上限。
- 数据保密等级、保留期和展示策略。

P1 使用 50-100 道双轨题：优先覆盖高风险协议、Tool Call、Coding 与关键推理。P2 扩展为完整 Coding 集、300-500 道通用/工具/协议题及安全红队集。

### 6.3 评分方式

确定性用例返回 `pass/fail` 和可解释失败码。开放回答采用盲评成对 Judge，并隐藏模型、渠道和答案顺序；交换答案顺序或使用多 Judge 以降低位置偏差。

能力指数使用 0-100 范围：

```text
能力域分数 = 100 * Σ(题目权重 * 归一化得分) / Σ题目权重
```

规则：

- P0 用例不被平均分稀释；任何新增 P0 失败独立触发门禁。
- 评分器版本变化必须生成新的分数版本，不覆盖旧结果。
- Judge 分歧超过配置阈值时进入复评，不直接算入最终分数。
- 公开总览展示分数、样本数、置信区间和数据新鲜度。

### 6.4 基线与候选

比较对象为经过审批的不可变基线和候选：

```text
基线：生产版本 + 已批准路由规则 + 固定题集/参数/评分器
候选：待发布版本或当前生产观察点
```

基线晋升条件：

1. 全部门禁通过。
2. 观察期无未关闭 P0/P1 告警。
3. Release Manager 与 Quality Admin 双方审批。
4. 保存题集、评分器、路由和构建制品版本。

## 7. 统计与降级判定

### 7.1 采样

- 确定性协议测试每个组合至少运行一次，失败时在不同 Worker 复验一次用于归因。
- 高波动模型能力题重复 3-5 次。
- 候选与基线使用相同题目、参数、区域和时间窗口成对运行。
- 样本不足、Judge 分歧过大或基础设施异常的结果不进入能力结论。

### 7.2 统计口径

```text
能力域差值 = 候选加权得分 - 基线加权得分
置信度     = 成对样本 Bootstrap 95% 置信区间
```

趋势检测同时使用：

- 24h/48h 固定窗口差值，便于产品展示。
- EWMA，用于平滑短期噪声。
- CUSUM，用于发现持续、小幅退化。

### 7.3 初始门禁

| 条件 | 默认动作 |
| --- | --- |
| P0 Coding、协议、Tool Call、计费新增失败 | 阻断发布 |
| 实际模型或路由与预期不一致 | P0 告警并阻断 |
| 任一关键能力域显著下降至少 3 个百分点 | 阻断或人工复核 |
| 综合能力显著下降至少 2 个百分点 | 阻断发布 |
| 截断率、异常拒答率、重试率、P99 超 SLO | 独立可靠性告警/门禁 |
| 样本不足或置信区间过宽 | 证据不足，不做降级结论 |

前两周为只记录观察期。观察期结束后，如果真实噪声未突破上述阈值，则直接启用；如需调整，必须通过规则变更记录说明历史波动、误报影响和新阈值，不得静默修改。

### 7.4 调度频率

```text
每 15 分钟：协议、路由、TTFT、结算哨兵集
每小时：关键 Coding、推理和 Tool Call 小样本
每日：完整双轨基线集
发布前：候选对基线全量评测 + 性能 + 安全回归
异常后：按账号池、渠道、区域和路由版本自动扩展诊断
```

## 8. 数据模型

### 8.1 核心实体

| 实体 | 关键内容 |
| --- | --- |
| `DatasetVersion` | 不可变题集版本、哈希、来源、状态 |
| `Case` | 用例、能力域、等级、评分器、执行策略 |
| `EvaluationPlan` | 触发器、模型/路由矩阵、预算、并发 |
| `EvaluationRun` | 一次批次、基线/候选、状态、汇总 |
| `Assignment` | Worker 租约、心跳、尝试和执行环境 |
| `Sample` | 某题某模型的一次运行与原始状态 |
| `RouteEvidence` | 实际模型、渠道、账号池、区域、回退链 |
| `Score` | 分数、失败码、解释、评分器版本 |
| `Baseline` | 已批准的比较基线和审批记录 |
| `GateDecision` | 规则版本、证据、结论和发布关联 |
| `Alert` | 严重性、影响切片、归因、处理与恢复 |

### 8.2 路由证据最小字段

```json
{
  "evaluation_run_id": "run_...",
  "sample_id": "sample_...",
  "route_trace_id": "trace_...",
  "requested_model": "model-alias",
  "resolved_model": "provider-model-id",
  "route_profile_version": "route-v42",
  "provider": "provider-name",
  "channel_id": "redacted-stable-id",
  "account_pool_id": "redacted-stable-id",
  "region": "region-code",
  "attempts": 1,
  "fallback_chain": [],
  "finish_reason": "stop",
  "input_tokens": 0,
  "output_tokens": 0,
  "ttft_ms": 0,
  "latency_ms": 0,
  "billed_amount": "0.000000"
}
```

`channel_id` 与 `account_pool_id` 使用稳定的脱敏标识。只有授权管理员可以通过审计流程映射到实际资源。

## 9. 存储、队列与任务状态机

### 9.1 存储分工

- PostgreSQL：计划、运行、租约、样本、分数、基线、门禁、告警与审计。
- Redis：任务通知、Worker 心跳、短期锁和并发控制。
- 对象存储：Patch、测试日志、最终响应与脱敏诊断 Artifact。
- Prometheus/Grafana：队列、Worker、网关、评分服务和 SLO 指标。

P1 使用 PostgreSQL 分区表保存结果与趋势，不引入新的分析数据库。当有效样本超过 1000 万或趋势查询持续影响事务数据库时，再通过 Outbox/CDC 将结果同步到 ClickHouse；PostgreSQL 仍是控制面事实源。

### 9.2 状态机

```text
pending
  -> leased
  -> running
  -> evidence_uploaded
  -> grading
  -> completed
```

异常终态包括 `infra_failed`、`upstream_failed`、`invalid_evidence`、`grading_failed` 和 `cancelled`。

任务采用“数据库为事实源、Redis 只负责通知”的租约模型。Worker 原子领取、定时续租；租约到期后任务可被其他 Worker 重新执行。所有步骤按以下键幂等：

```text
run_id + case_id + model_route + sample_index + attempt
```

一次有效样本只能生成一份当前评分；重新评分产生新版本，不能重复计入聚合。

## 10. 异常分类与处理

| 异常 | 分类 | 处理 |
| --- | --- | --- |
| 429、上游超时、连接断开 | 服务可靠性 | 有限重试；不计能力分，计可靠性指标 |
| 输出完整但答案错误 | 模型能力 | 正常评分 |
| SSE/JSON/Tool Call 协议错误 | 协议/网关 | 精确失败并根据 Trace 归因 |
| Worker、Docker、磁盘故障 | 测试基础设施 | 换 Worker 重试，不计模型失败 |
| Judge 超时 | 评分基础设施 | 切换 Judge 或延迟重评 |
| Judge 分歧过大 | 证据不足 | 多 Judge 或人工复核 |
| 路由证据缺失 | 可观测性缺陷 | 样本无效并触发 P1 告警 |
| 预算即将耗尽 | 预算保护 | 停低优先级任务，保留 P0 哨兵 |
| 题集或镜像哈希不符 | 可复现性缺陷 | 拒绝执行或拒绝计分 |

重试不能改变题目、Prompt、参数或路由目标。超过重试预算后保留原始错误作为可靠性证据，禁止“重试到成功”后隐藏失败率。

## 11. 控制台设计

控制台新增一级导航“质量雷达”。

### 11.1 雷达总览

- 模型健康状态、能力域分数、样本量、置信区间和数据新鲜度。
- 24h/48h 变化、P99、错误率、截断率和成本变化。
- 当前 P0/P1 告警、发布门禁与 Worker/队列健康。

### 11.2 模型矩阵

- 行：模型别名、路由配置或诊断切片。
- 列：Coding、推理、工具、协议、安全、性能、成本。
- 单元格：当前分、基线差值、置信度、样本量和趋势。

### 11.3 评测运行

- 计划、触发来源、模型矩阵、进度、预算、Worker 和失败分类。
- 支持受控复跑、取消低优先级任务和导出报告。

### 11.4 告警中心

异常详情包含：

```text
告警摘要
  -> 下降的能力域和起始时间
  -> 影响模型、渠道、账号池、区域和路由版本
  -> 基线/候选统计差异和置信区间
  -> 失败题目、响应 Diff 和评分解释
  -> 路由、重试、Token、延迟和结算证据
  -> 建议动作、审批记录和复测结果
```

### 11.5 题集与门禁

- 题集/评分器版本、用例稳定性和保密等级。
- 基线审批、阈值、调度、预算和发布规则。
- 所有变更写入审计日志。

## 12. 自动归因与处置闭环

### 12.1 初始归因规则

- 多个渠道同时下降：优先检查上游模型、题集或评分器变化。
- 单一渠道或账号池下降：优先检查路由、账号、区域或上游配额。
- 只有通过 `sub2api` 下降、官方直连正常：优先检查协议转换与网关。
- 能力稳定但 P99/错误率恶化：归为服务质量降级。
- 样本少、分歧大或证据不完整：归为证据不足。

### 12.2 处置流程

```text
发现异常
 -> 自动扩展诊断样本
 -> 确认归因
 -> 人工确认处置
 -> 隔离账号池 / 禁用渠道 / 回滚路由
 -> 自动复测
 -> 达标后恢复流量并关闭告警
```

雷达默认只建议，不自动切换生产流量。隔离、禁用、回滚和恢复必须经过 RBAC、二次确认和审计。P3 才允许对经过演练、风险可控的规则启用自动熔断。

## 13. 权限、安全与数据治理

### 13.1 角色

| 角色 | 权限 |
| --- | --- |
| Viewer | 查看脱敏雷达和报告 |
| Test Operator | 运行评测、复跑、管理 Worker |
| Quality Admin | 管理题集、评分器、阈值和基线 |
| Release Manager | 审批发布门禁与基线晋升 |
| Platform Admin | 执行渠道隔离、路由回滚和恢复 |

基线晋升需要 `Quality Admin + Release Manager` 双方审批。生产路由变更需要 `Platform Admin`，不能由评测 Worker 直接执行。

### 13.2 数据规则

- P1 仅使用公开题和平台维护的合成题。
- 不记录客户原始 Prompt，不从客户生产流量抽样。
- 不保存隐藏推理过程，只保存最终输出、工具调用和必要事件。
- Artifact 上传前执行密钥、凭据、个人信息和内部域名扫描。
- 原始响应默认保留 30 天，聚合指标和脱敏证据保留 13 个月。
- 安全用例和答案使用单独密钥加密并限制下载。
- Worker 无权读取生产数据库和上游账号明文凭据。

## 14. 流量、容量与预算隔离

- 使用专用评测租户、API Key、限流规则和预算账本。
- 哨兵任务设置独立并发上限，不能挤占客户保留容量。
- 每个计划必须配置每日/每次运行成本硬上限。
- 达到 80% 预算时告警，达到 100% 时停止非 P0 任务。
- 发布前全量评测需要显式预算审批。
- 真实上游与 Mock/录制回放分别计量，不能混合统计。
- 压测环境默认使用专用渠道或预发；生产只允许低速 Canary 哨兵。

## 15. 技术选型

### 15.1 核心实现

- Go：评测计划、状态机、基线、门禁、告警、权限与网关集成。
- Python：Benchmark runner、Coding verifier、统计与 Judge。
- Vue：雷达控制台。
- Docker/Kubernetes Job：隔离执行 Coding 和安全任务。
- PostgreSQL、Redis、对象存储：控制面、通知和 Artifact。
- OpenTelemetry、Prometheus、Grafana：Trace、指标和 SLO。

### 15.2 开源工具适配

| 工具 | 用途 | 集成方式 |
| --- | --- | --- |
| Promptfoo | 快速模型比较、断言、红队和 CI | 用例/Provider 适配器 |
| EvalScope | 标准 Benchmark、中文模型与性能评测 | Benchmark runner |
| DeepEval | Agent、Tool Call、JSON 与自定义指标 | Python 评分器库 |
| OpenCompass/lm-eval-harness | 标准和中文能力基线 | 离线任务适配器 |
| NVIDIA Garak | 越狱、注入和安全扫描 | 安全计划适配器 |
| k6 | 多租户 API/SSE 并发压测 | 独立性能计划 |
| Toxiproxy/Chaos Mesh | 网络、依赖和 K8s 故障注入 | 演练环境 |
| Langfuse | 可选的 LLM Trace/标注协作 | 非核心、按需对接 |

核心数据模型、基线、门禁和路由证据不能绑定某个外部工具。适配器只负责导入用例、执行或评分。

## 16. 分期交付

### P0：可观测基础

- `evaluation_run_id`、`sample_id` 与 `route_trace_id`。
- 脱敏路由证据 Schema。
- 专用评测租户、API Key、限流和预算。
- Trace、计费和路由版本关联。

### P1：MVP 雷达

- 受控 Worker 与独立评分器。
- 50-100 道 Coding、推理、工具和协议题。
- 模型矩阵、24h/48h 趋势、运行与告警视图。
- 只告警不阻断的两周观察期。

### P2：生产门禁

- 完整 Coding 与通用题集、安全集。
- 重复采样、置信区间、EWMA/CUSUM。
- Baseline 审批、发布前全量运行和强制门禁。
- 自动诊断账号池、渠道、区域和路由版本。

### P3：企业增强

- 多区域 Worker 与容灾验证。
- 客户私有题集和租户隔离报告。
- 安全红队与混沌演练编排。
- 经审批和演练的自动熔断规则。

## 17. 雷达自身测试策略

### 17.1 单元测试

- 评分公式、权重、缺失样本、重复样本和版本计算。
- Bootstrap、EWMA、CUSUM 与阈值边界。
- 状态机、租约、幂等键、预算和权限。

### 17.2 契约测试

- OpenAI、Anthropic、Gemini 和 SSE 事件协议。
- 评测上下文、Route Evidence 与计费 Schema。
- Worker、评分器、对象存储和 Admin API。

### 17.3 集成测试

- Mock 上游返回成功、错误、429、慢响应、断流和异常 Token。
- 路由回退、账号池隔离、区域故障和结算一致性。
- Worker 崩溃、租约过期、重复通知、重复上传和评分重试。

### 17.4 端到端测试

- 已知好/坏模型或固定响应代理验证降级检测。
- 注入协议字段丢失、Tool Call 参数错误和 SSE 截断。
- 注入性能回归和渠道故障，验证归因与告警。
- 基线审批、发布阻断、人工豁免、路由回滚和恢复复测。

### 17.5 生产验证

- 影子运行期间对客户 SLO、账单和路由无影响。
- 评测任务达到预算或并发上限时能安全停止。
- Dashboard 聚合与原始样本抽查一致。
- 告警演练能够在约定时间内定位到责任切片。

## 18. SLO 与运营指标

### 18.1 雷达平台 SLO

- 15 分钟哨兵任务 95% 在下一个周期开始前完成。
- 评测任务状态与路由证据关联成功率不低于 99.9%。
- 已完成样本的评分结果 99% 在 10 分钟内可见。
- P0 告警从有效证据生成到通知不超过 5 分钟。
- 重复计分率为 0。

### 18.2 质量运营指标

- 有效样本率、基础设施失败率和用例不稳定率。
- 告警精确率、误报率、漏报演练结果和平均确认时间。
- 从异常发现到归因、处置、复测和恢复的耗时。
- 每个模型/能力域的评测成本与覆盖率。
- 发布门禁阻断次数、人工豁免次数和豁免后事故数。

## 19. 管理与发布流程

1. 质量团队维护题集、评分器和用例稳定性。
2. 平台团队维护路由证据、Worker 和控制面。
3. SRE 维护雷达 SLO、告警通道、容量和故障演练。
4. Release Manager 审批基线、门禁与发布豁免。
5. 每月评审覆盖率、成本、误报、漏报和阈值变更。

发布豁免必须记录：失败门禁、业务理由、风险接受人、临时缓解措施、有效期和补测计划。豁免到期自动失效。

## 20. 风险与缓解

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| 公共题数据污染 | 分数虚高 | 私有合成题、隐藏测试、定期轮换 |
| 模型输出随机 | 误报 | 重复采样、成对比较、置信区间 |
| Judge 偏差 | 错误结论 | 盲评、换序、多 Judge、人工校准 |
| Worker 环境漂移 | 结果不可比 | 镜像/依赖哈希、受控资源、禁止隐式升级 |
| 上游限流 | 能力误判 | 可靠性与能力分离、专用配额、有限重试 |
| 路由证据被伪造 | 归因错误 | 服务端签发上下文、内部 Trace、不可由客户覆盖 |
| 评测成本失控 | 影响预算 | 硬预算、优先级、停止阈值和审批 |
| 雷达影响生产 | 客户 SLO 下降 | 独立租户/并发池、预发压测、生产低速哨兵 |
| 自动处置扩大故障 | 生产事故 | P1/P2 人工确认，P3 仅开放已演练规则 |

## 21. 已确认决策

- 目标平台为 `sub2api`。
- 采用平台自建受控 Worker，不采用社区众测作为主数据源。
- 第一版采用 Coding/SWE 与通用推理/工具双轨雷达。
- 采用嵌入式质量控制面，Worker 与评分器独立部署。
- 使用能力指数而不是通用 IQ，能力域分别计分和门禁。
- 第一阶段不采集客户原始 Prompt，不自动切换生产流量。
- 第一阶段复用 PostgreSQL/Redis；达到明确规模阈值后再引入 ClickHouse。
