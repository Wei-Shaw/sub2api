# Sub2API 服务器维护手册

> 文档版本：v1.0
>
> 最后更新：2026-07-29
>
> 适用环境：AWS EC2（Amazon Linux 2023）+ Docker Compose + PostgreSQL + Redis
>
> 维护原则：先观察、再变更；先备份、再升级；一次只改一个变量。

## 1. 文档目的

本文用于 Sub2API 生产服务器的日常巡检、监控、备份、升级、故障处理和安全维护。执行任何变更前，应先确认当前实例、容器和部署目录，避免误操作其他环境。

本文命令默认由 `ec2-user` 执行。涉及系统日志、软件更新等操作时需要 `sudo`。

## 2. 当前环境基线

### 2.1 AWS 资源

| 项目 | 当前值 | 说明 |
| --- | --- | --- |
| 区域 | `ap-northeast-1` | 东京区域 |
| EC2 实例 ID | `i-0e54fc7a3f3d399d5` | SSM/SSH 连接目标 |
| 实例类型 | `t3.micro` | 2 vCPU、约 1 GiB 内存，突发型 CPU |
| 根磁盘 | gp3，8 GiB | 当前约使用 59%，剩余约 3.3 GiB |
| EBS 性能 | 4000 IOPS、200 MiB/s | 当前配置足够，需继续观察峰值与延迟 |
| Swap | 1 GiB | 已使用约 181 MiB，说明历史上出现过内存压力 |
| 管理通道 | AWS Systems Manager Session Manager | 本地通过 SSH ProxyCommand 使用 |

公有 IP 可能变化，不作为日常连接入口。实例 ID 和 SSM 是主要运维通道。

### 2.2 服务拓扑

| 容器 | 作用 | 数据位置 | 对宿主机开放端口 |
| --- | --- | --- | --- |
| `sub2api` | API、管理后台和业务逻辑 | `/app/data` | 默认 `8080` |
| `sub2api-postgres` | PostgreSQL 18 | `/var/lib/postgresql/data` | 不开放 |
| `sub2api-redis` | Redis 8 | `/data` | 不开放 |

应用健康检查地址为：`http://127.0.0.1:8080/health`。

### 2.3 当前容量判断

当前空闲状态下，主机可用内存约 182 MiB：

- `sub2api` 约 205 MiB；
- PostgreSQL 约 106 MiB；
- Redis 约 9 MiB；
- 操作系统、Docker、SSM Agent 和缓存占用其余内存。

结论：当前 CPU 和磁盘没有明显瓶颈，但内存余量很低。`t3.micro` 适合测试、低活跃流量或短期观察，不适合作为“50 个请求持续同时执行”的稳定生产配置。

容量建议：

| 实际负载 | 建议配置起点 |
| --- | --- |
| 50 个注册用户，平时少量用户同时请求 | 可暂留 `t3.micro`，必须监控内存、Swap 和 CPU 积分 |
| 约 10～20 个持续并发请求 | 至少 2 GiB 内存，压测后决定是否继续升级 |
| 约 50 个持续并发/流式请求 | 建议从 4 GiB 开始压测；长连接多或请求重时使用 8 GiB |

“用户数”不等于“并发请求数”。最终规格必须依据高峰期并发请求、响应时长、内存峰值和 CPU 积分确定。

## 3. 登录与授权

### 3.1 日常登录

本地终端执行：

```bash
ssh sub2api
```

该命令通过 SSM 建立 SSH 通道，不依赖固定公网 IP，也不需要向全网开放 22 端口。

### 3.2 AWS 临时授权过期

如果出现凭证过期、SSO/登录失效或 SSM 无法启动，执行：

```bash
sub2api-login
ssh sub2api
```

也可以手动重新授权：

```bash
aws login --profile sub2api --region ap-northeast-1
aws sts get-caller-identity --profile sub2api
ssh sub2api
```

### 3.3 登录后确认目标

```bash
hostname
cat /etc/os-release
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}'
```

预期能看到 `sub2api`、`sub2api-postgres` 和 `sub2api-redis` 三个容器。

### 3.4 自动定位部署目录

不要猜测 Compose 文件位置。登录服务器后执行：

```bash
DEPLOY_DIR=$(docker inspect sub2api --format '{{ index .Config.Labels "com.docker.compose.project.working_dir" }}')
printf '部署目录：%s\n' "$DEPLOY_DIR"
cd "$DEPLOY_DIR"
```

如果结果为空，先执行以下命令查看容器标签和挂载目录，再人工确认：

```bash
docker inspect sub2api --format '{{json .Config.Labels}}'
docker inspect sub2api --format '{{range .Mounts}}{{println .Source "->" .Destination}}{{end}}'
```

## 4. 日常巡检

### 4.1 本地一条命令完成基础巡检

```bash
ssh sub2api 'date; uptime; free -h; df -h /; vmstat 1 5; docker stats --no-stream; docker ps --format "table {{.Names}}\t{{.Status}}"'
```

持续观察，每 5 秒刷新一次：

```bash
ssh -t sub2api "watch -n 5 'uptime; free -h; df -h /; docker stats --no-stream'"
```

按 `Ctrl+C` 退出。

### 4.2 登录服务器后的完整巡检

```bash
date
uptime
free -h
df -h /
vmstat 1 5
docker stats --no-stream
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}'
curl -fsS http://127.0.0.1:8080/health && echo
```

### 4.3 指标解释与告警线

| 指标 | 正常参考 | 警告 | 严重 |
| --- | --- | --- | --- |
| CPU 使用率 | 高峰后能回落 | 持续超过 80% 5 分钟 | 持续超过 90%，请求明显变慢 |
| Load Average | 对 2 vCPU 通常低于 2 | 持续高于 2 | 持续高于 4 |
| `available` 内存 | 大于 300 MiB 更稳妥 | 小于 200 MiB | 小于 100 MiB 或发生 OOM |
| `vmstat` 的 `si/so` | 持续为 0 | 间歇出现 | 连续非 0，且服务延迟升高 |
| 根磁盘使用率 | 小于 70% | 超过 80% | 超过 90% |
| `vmstat` 的 `wa` | 低于 5% | 持续超过 10% | 持续超过 20% |
| EBS IOPS | 低于 3200 | 接近 4000 | 达到上限且队列/延迟升高 |
| EBS 吞吐量 | 低于 160 MiB/s | 接近 200 MiB/s | 达到上限且队列/延迟升高 |
| 健康检查 | HTTP 200 | 偶发失败 | 连续失败 |

Swap 中存在数据不等于当前仍在换页；重点观察 `vmstat` 的 `si`、`so` 是否持续非 0，以及可用内存是否继续下降。

### 4.4 容器与健康检查

```bash
docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'
docker inspect sub2api --format 'health={{if .State.Health}}{{.State.Health.Status}}{{else}}not-configured{{end}}'
curl -i --max-time 10 http://127.0.0.1:8080/health
```

数据库和 Redis 检查：

```bash
docker exec sub2api-postgres sh -lc 'pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
docker exec sub2api-redis redis-cli ping
```

### 4.5 日志检查

查看最近 10 分钟应用日志：

```bash
docker logs --since 10m --tail 200 sub2api
```

实时跟踪：

```bash
docker logs -f --since 5m sub2api
```

查看三个容器的近期日志：

```bash
DEPLOY_DIR=$(docker inspect sub2api --format '{{ index .Config.Labels "com.docker.compose.project.working_dir" }}')
cd "$DEPLOY_DIR"
docker compose logs --since 10m --tail 200
```

如果启用了文件日志，可检查容器内日志目录：

```bash
docker exec sub2api sh -lc 'ls -lh /app/data/logs 2>/dev/null || true'
docker exec sub2api sh -lc 'tail -n 200 /app/data/logs/sub2api.log 2>/dev/null || true'
```

## 5. AWS CloudWatch 监控

### 5.1 EC2 必看指标

- `CPUUtilization`：CPU 使用率；
- `CPUCreditBalance`：t3 实例剩余 CPU 积分；
- `CPUSurplusCreditBalance`：无限模式下借用的积分；
- `NetworkIn`、`NetworkOut`：网络流量；
- `StatusCheckFailed`：实例或系统状态检查失败。

对 `t3.micro`，CPU 使用率暂时正常并不代表长期有足够算力。`CPUCreditBalance` 持续下降并接近 0 时，应降低负载或升级实例。

### 5.2 EBS 必看指标

- `VolumeReadOps`、`VolumeWriteOps`；
- `VolumeReadBytes`、`VolumeWriteBytes`；
- `VolumeQueueLength`；
- 读写延迟；
- 突发期间是否接近 4000 IOPS 或 200 MiB/s。

### 5.3 内存和磁盘告警

EC2 默认指标不包含操作系统内存使用率和磁盘空间。需要安装并配置 CloudWatch Agent，才能持续上报 `mem_used_percent`、`disk_used_percent`、Swap 等指标。

建议创建以下告警：

- CPU 连续 5 分钟超过 80%；
- CPUCreditBalance 低于 20；
- 可用内存低于 200 MiB；
- 根磁盘使用率超过 80%；
- 实例状态检查失败；
- 应用健康检查连续失败。

## 6. 资源配置核查

### 6.1 查看实际生效配置

只查看非敏感调优项，不输出密码和密钥：

```bash
docker inspect sub2api --format '{{range .Config.Env}}{{println .}}{{end}}' \
  | grep -E '^(DATABASE_MAX_OPEN_CONNS|DATABASE_MAX_IDLE_CONNS|REDIS_POOL_SIZE|REDIS_MIN_IDLE_CONNS)='

docker inspect sub2api-postgres --format '{{json .Config.Cmd}}'
```

数据库连接统计：

```bash
docker exec sub2api-postgres sh -lc \
  'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "select state, count(*) from pg_stat_activity group by state order by state;"'
```

### 6.2 `t3.micro` 保守起点

仓库 `.env.example` 含有面向大内存、高并发环境的示例值，例如较大的 PostgreSQL 缓冲区、数据库连接池和 Redis 连接池。这些值不适合直接用于当前约 1 GiB 主机。

当前主机可从以下范围开始压测：

```dotenv
POSTGRES_MAX_CONNECTIONS=50
POSTGRES_SHARED_BUFFERS=128MB
POSTGRES_EFFECTIVE_CACHE_SIZE=512MB
POSTGRES_MAINTENANCE_WORK_MEM=32MB

DATABASE_MAX_OPEN_CONNS=20
DATABASE_MAX_IDLE_CONNS=5

REDIS_POOL_SIZE=50
REDIS_MIN_IDLE_CONNS=5
```

这些是保守起点，不是固定答案。修改前先记录当前值并备份 `.env`，修改后只重建相关容器，然后观察 3～24 小时。不要同时修改多个容量参数。

## 7. 备份

### 7.1 备份原则

- 升级、迁移和高风险配置变更前必须备份；
- PostgreSQL 逻辑备份是核心，应用数据目录也必须保存；
- `.env` 含密钥，只能加密保存，不得提交到 Git 或发送到聊天记录；
- 备份文件不能只保存在同一块 8 GiB 系统盘；
- 每月至少进行一次恢复演练，未验证的备份不能视为可用备份。

### 7.2 创建备份目录

```bash
DEPLOY_DIR=$(docker inspect sub2api --format '{{ index .Config.Labels "com.docker.compose.project.working_dir" }}')
cd "$DEPLOY_DIR"
BACKUP_DIR="$DEPLOY_DIR/backups"
BACKUP_TIME=$(date +%Y%m%d-%H%M%S)
mkdir -p "$BACKUP_DIR"
chmod 700 "$BACKUP_DIR"
df -h "$DEPLOY_DIR"
```

当前根磁盘只有约 3.3 GiB 可用空间。开始前必须确认“数据库备份 + 应用数据备份 + 安全余量”不会占满磁盘，完成后立即复制到加密的离机存储，并按保留策略清理已确认可恢复的旧备份。

### 7.3 PostgreSQL 在线逻辑备份

```bash
docker exec sub2api-postgres sh -lc \
  'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' \
  > "$BACKUP_DIR/sub2api-db-$BACKUP_TIME.dump"
```

验证文件非空并检查归档目录：

```bash
test -s "$BACKUP_DIR/sub2api-db-$BACKUP_TIME.dump"
docker exec -i sub2api-postgres pg_restore -l \
  < "$BACKUP_DIR/sub2api-db-$BACKUP_TIME.dump" \
  | head -n 20
```

### 7.4 应用数据备份

直接从容器输出压缩流，避免在小容量系统盘上同时保留未压缩目录和压缩包：

```bash
docker exec sub2api sh -lc 'tar -C /app/data -czf - .' \
  > "$BACKUP_DIR/sub2api-data-$BACKUP_TIME.tar.gz"
```

确认压缩包可读取：

```bash
test -s "$BACKUP_DIR/sub2api-data-$BACKUP_TIME.tar.gz"
tar -tzf "$BACKUP_DIR/sub2api-data-$BACKUP_TIME.tar.gz" | head
```

### 7.5 配置文件备份

如果部署目录存在 `.env`：

```bash
install -m 600 .env "$BACKUP_DIR/env-$BACKUP_TIME"
```

该文件包含数据库密码、JWT 密钥和 TOTP 加密密钥，离机保存前必须使用公司认可的加密方式。

### 7.6 Redis 备份说明

Redis 当前启用了 AOF 和 RDB。它主要承载缓存和临时状态，PostgreSQL 才是主要业务数据源。需要迁移 Redis 状态时，不要只复制正在写入的 AOF 文件；应安排维护窗口，停止应用写入后对整个 Redis 数据目录/卷做一致性快照。

日常可触发并确认一次 RDB 快照：

```bash
docker exec sub2api-redis redis-cli BGSAVE
docker exec sub2api-redis sh -lc \
  'redis-cli INFO persistence | grep -E "^(rdb_bgsave_in_progress|rdb_last_bgsave_status|rdb_last_save_time):"'
```

## 8. 安全升级流程

### 8.1 升级前检查

```bash
DEPLOY_DIR=$(docker inspect sub2api --format '{{ index .Config.Labels "com.docker.compose.project.working_dir" }}')
cd "$DEPLOY_DIR"
docker compose ps
curl -fsS http://127.0.0.1:8080/health && echo
docker inspect sub2api --format 'image={{.Config.Image}} image_id={{.Image}}'
df -h /
free -h
```

记录当前镜像标签和镜像 ID，并按第 7 节完成数据库、应用数据和配置备份。

### 8.2 拉取并更新

```bash
docker compose pull
docker compose up -d
```

不要使用 `docker compose down -v`。`-v` 会删除命名卷，可能导致数据库、Redis 和应用数据不可恢复。

### 8.3 升级后验证

```bash
docker compose ps
curl -fsS http://127.0.0.1:8080/health && echo
docker compose logs --since 10m --tail 200 sub2api
docker exec sub2api-postgres sh -lc 'pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
docker exec sub2api-redis redis-cli ping
```

同时人工验证：

1. 管理后台可以登录；
2. 用户列表、订阅和账号数据正常；
3. 发起一个真实但低成本的 API 请求；
4. 检查错误率、响应时长、内存和 CPU；
5. 连续观察至少 15～30 分钟再结束变更窗口。

### 8.4 回滚原则

数据库迁移是前向执行的，仅切回旧镜像不一定能回滚数据库结构。因此：

- 生产环境不要长期使用无法追踪的 `latest` 作为唯一回滚依据；
- 升级前记录旧镜像 tag/digest；
- 保留升级前数据库备份和应用数据备份；
- 优先将镜像固定到明确版本或 digest；
- 发生严重问题时先停止应用写入，再评估“旧镜像 + 数据库恢复”是否兼容。

数据库恢复属于高风险操作，只能在维护窗口执行，步骤见第 10.6 节。

## 9. 日常启停操作

先进入部署目录：

```bash
DEPLOY_DIR=$(docker inspect sub2api --format '{{ index .Config.Labels "com.docker.compose.project.working_dir" }}')
cd "$DEPLOY_DIR"
```

只重启应用，影响最小：

```bash
docker compose restart sub2api
```

重建应用容器，使 `.env` 配置生效：

```bash
docker compose up -d --no-deps --force-recreate sub2api
```

查看状态和日志：

```bash
docker compose ps
docker compose logs --since 5m --tail 200 sub2api
```

只有数据库或 Redis 确认异常时，才单独重启对应容器。不要把“重启全部服务”作为第一排错手段。

## 10. 常见故障处理

### 10.1 服务无法访问或返回 502/503

含义：反向代理无法连接应用，或应用健康检查失败。

按顺序执行：

```bash
docker ps -a --format 'table {{.Names}}\t{{.Status}}'
curl -i --max-time 10 http://127.0.0.1:8080/health
docker logs --since 15m --tail 300 sub2api
ss -lntp | grep ':8080'
```

最可能原因按优先级排序：

1. 应用容器退出或健康检查失败；
2. PostgreSQL/Redis 未就绪，应用启动被阻塞；
3. 内存不足，应用被 OOM Killer 终止；
4. 端口、反向代理或安全组配置错误；
5. 升级后的配置或数据库迁移失败。

仅当应用容器自身异常且数据服务正常时，执行：

```bash
docker restart sub2api
```

### 10.2 内存不足或 Swap 持续增长

```bash
free -h
vmstat 1 10
docker stats --no-stream
sudo journalctl -k --since '-30 min' | grep -Ei 'oom|out of memory|killed process'
```

处理顺序：

1. 找出内存增长最快的容器；
2. 降低请求并发和连接池；
3. 检查异常日志、慢请求和连接泄漏；
4. 必要时只重启异常应用容器止血；
5. 如果高峰期长期不足，升级到 2～4 GiB 或更高内存实例。

Swap 只能缓冲突发，不能替代物理内存。不要通过无限增大 Swap 解决持续内存不足。

### 10.3 CPU 高、响应慢

```bash
uptime
vmstat 1 10
docker stats --no-stream
ps -eo pid,ppid,cmd,%cpu,%mem --sort=-%cpu | head -n 15
```

同时在 CloudWatch 查看 `CPUUtilization` 和 `CPUCreditBalance`。如果 CPU 积分接近 0，即使应用没有故障，t3 实例也可能受到基线性能限制。

### 10.4 磁盘空间不足

```bash
df -h /
docker system df
sudo du -xhd1 /var/lib/docker 2>/dev/null | sort -h
sudo journalctl --disk-usage
```

优先处理可确认无用的旧日志、过期备份和未使用镜像。删除前列出目标并确认用途。

禁止直接执行：

```text
docker system prune -a --volumes
docker compose down -v
rm -rf postgres_data redis_data data
```

这些命令可能删除仍需使用的镜像、命名卷或业务数据。

### 10.5 PostgreSQL 或 Redis 异常

PostgreSQL：

```bash
docker logs --since 15m --tail 300 sub2api-postgres
docker exec sub2api-postgres sh -lc 'pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
docker exec sub2api-postgres sh -lc \
  'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "select state, count(*) from pg_stat_activity group by state;"'
```

Redis：

```bash
docker logs --since 15m --tail 300 sub2api-redis
docker exec sub2api-redis redis-cli ping
docker exec sub2api-redis sh -lc \
  'redis-cli INFO memory | grep -E "^(used_memory_human|maxmemory_human|mem_fragmentation_ratio):"'
```

如果数据服务频繁异常，不要反复重启；先检查内存、磁盘空间、文件系统错误和配置是否超过主机容量。

### 10.6 PostgreSQL 恢复（高风险）

仅在以下条件全部满足时执行：

- 已确认备份能通过 `pg_restore -l` 读取；
- 已记录当前数据状态并额外备份；
- 已通知用户进入维护窗口；
- 已确认备份版本与目标应用版本兼容；
- 已停止所有写入。

恢复示例：

```bash
DEPLOY_DIR=$(docker inspect sub2api --format '{{ index .Config.Labels "com.docker.compose.project.working_dir" }}')
cd "$DEPLOY_DIR"
docker compose stop sub2api

docker exec -i sub2api-postgres sh -lc \
  'pg_restore --clean --if-exists --no-owner -U "$POSTGRES_USER" -d "$POSTGRES_DB"' \
  < /绝对路径/备份文件.dump

docker compose start sub2api
curl -fsS http://127.0.0.1:8080/health && echo
```

如果恢复命令报错，不要继续覆盖或删除数据卷，应保留完整输出并重新评估。

### 10.7 SSM/SSH 无法连接

先在本地确认临时授权：

```bash
sub2api-login
aws sts get-caller-identity --profile sub2api
ssh sub2api
```

如果授权正常但连接仍失败，通过 AWS 控制台的 Session Manager 备用入口登录实例，然后检查：

```bash
sudo systemctl status amazon-ssm-agent --no-pager
sudo journalctl -u amazon-ssm-agent --since '-15 min' --no-pager
sudo systemctl status sshd --no-pager
sudo ss -lntp | grep ':22'
```

只有确认 Agent 卡死时才重启：

```bash
sudo systemctl restart amazon-ssm-agent
sudo systemctl status amazon-ssm-agent --no-pager
```

排查优先级：本地 AWS 授权过期、实例 SSM 在线状态、实例 IAM 角色、实例到 AWS SSM 端点的网络、SSH 服务。由于日常连接走 SSM，公网 IP 不固定不会影响正常登录。

## 11. 安全维护

### 11.1 SSH 与安全组

当前已验证 SSM 登录可用。安全组若仍允许 `0.0.0.0/0` 访问 22 端口，属于不必要的公网暴露风险。

关闭公网 SSH 前必须确认：

1. 所有维护人员都能通过 SSM 登录；
2. 实例角色 `sub2api-ssm-role` 正常；
3. `amazon-ssm-agent` 在线；
4. 实例能访问 SSM 所需的 AWS 端点；
5. 已保留 AWS 控制台 Session Manager 作为备用入口。

确认后，可删除公网 `0.0.0.0/0:22` 规则，或仅保留明确需要的受控来源。安全组修改应单独安排变更，不与应用升级同时进行。

### 11.2 密钥与配置

- `.env` 权限保持为 `600`；
- 私钥权限保持为 `400`；
- 不在终端截图、工单、Git、聊天或日志中暴露密码和密钥；
- 不随意更换 `JWT_SECRET`，否则现有登录会话可能失效；
- 不随意更换 `TOTP_ENCRYPTION_KEY`，否则现有 2FA 配置可能无法解密；
- 管理员密码、数据库密码和 AWS 权限按最小权限原则管理；
- 定期审计 IAM 角色、安全组和 CloudTrail 登录记录。

### 11.3 系统补丁

先查看可更新项目：

```bash
sudo dnf check-update
```

系统更新可能影响 Docker、内核和网络，应安排维护窗口并先创建备份。需要重启时，先确认容器使用 `restart: unless-stopped`，重启后立即执行完整巡检。

## 14. 快速命令表

```bash
# 本地重新授权并登录
sub2api-login && ssh sub2api

# 本地一次性巡检
ssh sub2api 'date; uptime; free -h; df -h /; vmstat 1 5; docker stats --no-stream'

curl -fsS http://127.0.0.1:8080/health && echo

# 容器状态
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}'

# 应用近期日志
docker logs --since 10m --tail 200 sub2api

# 实时日志
docker logs -f --since 5m sub2api

# 只重启应用
docker restart sub2api

# 数据库健康
docker exec sub2api-postgres sh -lc 'pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB"'

# Redis 健康
docker exec sub2api-redis redis-cli ping

# OOM 检查
sudo journalctl -k --since '-30 min' | grep -Ei 'oom|out of memory|killed process'

# Docker 磁盘占用
docker system df
```
