## Context

系统已有两套不适合本需求的凭证：`api_keys` 参与模型路由、额度和计费，`inner_api_apps` 是管理员管理的全局 RPC 接入方。COS 服务已经封装上传、删除和可选的服务端 `CopyObject`，素材服务也已有基于用户 ID 与 `account_id` 派生的不可枚举目录，但 `AddMaterialByURL` 目前只登记 URL。

本变更横跨凭证持久化、HTTP 鉴权、对象存储和控制台个人菜单。关键约束是开发者密钥不能扩大现有 API Key 权限，且所有由文件 API 写入或删除的对象都必须可从 key 路径验证用户归属。

## Goals / Non-Goals

**Goals:**

- 提供可独立吊销、只用于开发者文件 API 的用户级密钥。
- 提供流式上传和按 URL 删除的文件暂存 API，并把对象严格限制在 COS 配置 prefix 下的 `file_uploads` 目录。
- 将属于当前用户的暂存文件通过 COS 服务端复制加删除移动到素材目录。
- 在个人菜单中提供无需跳转页面的密钥创建、一次性展示和删除体验。
- 提高素材库列表密度，并让用户仅修改自己素材的展示文件名。

**Non-Goals:**

- 不让开发者密钥访问模型、余额、素材列表或其他登录态 API。
- 不把文件 API 扩展成长期文件管理器，不提供列表、重命名或跨用户共享。
- 不改变普通 URL 导入素材时的 SSRF 下载流程，也不迁移历史素材数据。
- 素材改名不移动或复制 COS 对象，也不改变现有素材 URL。

## Decisions

### 1. 使用独立的 `developer_keys` 表和摘要鉴权

表记录 `user_id`、名称、密钥显示前缀、SHA-256 摘要、最近使用时间和时间戳。密钥格式使用固定前缀加足够长度的加密随机串；明文只在创建响应出现一次，后续列表永不返回。

选择独立表是为了从数据模型和中间件层面隔离权限。复用 `api_keys` 会把文件访问凭证带入计费、分组和模型路由语义；复用 `inner_api_apps` 则无法表达用户归属，且会把普通用户放进管理员管理面。

### 2. 管理 API 使用 JWT，文件 API 使用专用 Bearer 中间件

登录用户通过 `GET/POST /user/developer-keys` 和 `DELETE /user/developer-keys/:id` 管理自己的密钥。`/api/v1/file/` 只接受 `Authorization: Bearer <developer-key>`，中间件查询摘要并把用户 ID 与密钥 ID写入 Gin context；删除密钥即刻使鉴权失败。

该边界避免在通用 API Key 中间件中加入特殊分支，也让未来为开发者 API 增加独立限流和审计更直接。

### 3. 暂存对象归属由不可枚举 key 前缀表达

完整对象 key 为 `<cos-prefix>/file_uploads/<opaque-user-prefix>/<yyyy>/<mm>/<uuid><ext>`。`opaque-user-prefix` 复用素材服务基于用户 ID、`account_id` 和服务端密钥派生的标识。上传文件名只用于推断安全扩展名，不直接进入对象 key。

删除请求传公开 URL。服务端先验证 URL 与当前 COS 公网 origin 完全一致，再解析对象 key，并要求它位于当前用户的暂存前缀下。相比由客户端直接提交 key，这可直接使用上传响应，同时不会允许任意桶对象删除。

### 4. 上传流式写入对象存储并设 512 MiB 上限

POST 使用 `multipart/form-data` 的 `file` 字段。处理器和 COS 服务通过受限 reader 流式传输，不把大文件整体读入内存；空文件和超过 512 MiB 的文件在写入前或读取过程中拒绝。成功响应返回 `url`、`size` 和 `content_type`。

512 MiB 与现有素材视频上限一致，可支持图片、音频和视频，同时限制通用暂存接口的成本。暂存目录不是永久网盘，生命周期清理由后续运维策略处理。

### 5. `AddMaterialByURL` 只移动当前用户的暂存对象

素材服务识别 URL 是否位于配置的 `file_uploads` 根目录。若是当前用户对象，则生成现有 `users/<opaque>/materials/...` 目标 key，调用 COS `MoveFile`（`CopyObject` 后删除源）并保存目标 URL 与 key；若位于其他用户前缀则拒绝。非 `file_uploads` 的同源 COS URL继续按现有逻辑登记。

数据库写入失败时尝试把对象移回原 key；回滚失败会记录错误。对象存储不提供原子 rename，因此复制成功而删除失败可能短暂留下两份对象，错误会向上返回而不会登记不确定状态。

### 6. 用户素材改名仅更新展示字段

登录用户通过 `PATCH /api/v1/user/materials/:id` 提交 `file_name`。服务层校验名称非空且不超过数据库字段限制，仓储在同一条 `UPDATE` 中同时约束素材 ID、当前用户 ID 和未删除状态，并返回更新后的素材 DTO。

此处的“改名”只更新 `user_materials.file_name`，不调用 COS `MoveFile`，因此已被任务或外部系统引用的 URL 保持稳定。前端使用窄屏可用的弹窗编辑名称，并在成功后原地更新卡片。素材网格使用约 180px 的最小卡宽自动填充，在密度和预览辨识度之间取中间档。图片预览区可打开大图弹窗，弹窗按原始比例展示并约束在当前视口内，不额外下载或转换图片。

## Risks / Trade-offs

- [对象移动不是原子操作] → `MoveFile` 只有复制和删除都成功才返回成功，并记录部分失败；素材落库失败时执行反向移动补偿。
- [仅凭路径表达暂存归属，无法列出用户上传历史] → 本需求不提供列表；随机 key 与严格用户前缀校验足以支持上传、删除和迁移。
- [密钥摘要查询仍可离线暴力尝试] → 密钥使用至少 256 bit 随机熵，固定前缀不参与安全性；数据库不保存明文。
- [大文件可能耗尽连接或对象存储费用] → 采用 512 MiB 硬限制、专用限流，并在请求和存储层使用流式传输。

## Migration Plan

1. 部署数据库迁移与后端代码；新表为空，不影响既有请求。
2. 部署前端入口和弹窗；COS 或开发者密钥加密/路径配置不可用时，后端返回明确错误。
3. 回滚应用代码时可保留 `developer_keys` 表；它不会被旧版本读取。完全回滚可在确认无使用后删除该表。

## Open Questions

无。API 请求形态、单文件上限、密钥展示策略和对象目录规则均在本变更中固定。
