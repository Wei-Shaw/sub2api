## Context

当前管理端的版本徽标会主动请求系统更新接口，而系统更新接口又会调用 GitHub Release 查询最新版本。这样一来，“显示当前版本”被错误地扩展成“探测远端发布状态”，把展示职责、运维决策和发布渠道耦合在一起。

产品后续要脱离 GitHub 主版本更新，这意味着 GitHub 不再是可信的发布源。继续保留这条链路，既会产生误导性的更新提示，也会让系统保留一套已经失效的在线更新与回滚行为。

## Goals / Non-Goals

- Goals:
  - 让版本徽标只表达当前构建版本，不再表达 GitHub 远端状态
  - 移除 GitHub 驱动的更新检查、在线更新、回滚入口及依赖
  - 保留与版本更新机制无关的服务重启能力
- Non-Goals:
  - 这次不引入新的自有更新源或发布中心
  - 这次不重做完整的软件分发与升级体系
  - 这次不改变构建版本号的注入方式

## Decisions

- Decision: 管理端版本徽标退回为纯本地版本展示
  - Why: 版本展示的职责是表达当前运行实例，而不是替运维推断远端是否有更新
  - Alternative considered: 仅隐藏更新提示点，保留后台检测
  - Rejected because: 这只会把错误耦合藏起来，后台仍会继续依赖 GitHub 并保留无效调用

- Decision: 系统版本接口只返回当前构建版本，不再调用远端更新检查
  - Why: 当前版本是本地构建事实，不应依赖网络或第三方发布源
  - Alternative considered: 继续复用现有更新服务，只忽略 `has_update`
  - Rejected because: 读取本地版本却触发远端探测，本身就是职责混乱

- Decision: 下线在线更新与回滚 API，而不是仅在前端隐藏入口
  - Why: 产品已明确脱离 GitHub 主版本更新，保留这些入口只会留下错误能力与运维歧义
  - Alternative considered: 保留后端 API 以备未来可能重用
  - Rejected because: 这是典型的 YAGNI，且会让无效能力继续占用测试与维护成本

## Risks / Trade-offs

- 风险: 失去现有“一键更新/回滚”能力
  - Mitigation: 当前发布策略已经不再依赖 GitHub 主版本更新，保留这套能力只会制造错误预期

- 风险: 现有前后端测试会因为接口下线而失败
  - Mitigation: 同步清理测试桩与路由断言，确保行为边界与当前产品策略一致

## Migration Plan

1. 先移除前端更新探测与提示交互
2. 再收缩系统管理 API，只保留当前版本与重启能力
3. 最后清理 GitHub Release 更新服务、依赖注入和相关测试

## Open Questions

- 后续若引入自有发布中心，是否需要新的只读“发布通道状态”能力，而不是恢复在线更新入口
